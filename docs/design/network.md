## 前提と要件

- ゲーム: トップダウン視点の F1 風レースゲーム (Canvas 2D、固定 60fps 更新)
- 接続形態: P2P のホスト・クライアント方式。マッチング・シグナリング (接続情報の仲介)・中継のサーバーは用意しない
- 接続方法: ホストが参加者ごとに「招待リンク」を発行し、チャット (Discord、LINE など) で手渡しする。参加者はリンクを開き、できた「返答コード」を送り返す
- 人数: 最大 8 人
- 想定環境: 同一 LAN、およびインターネット越し (ポート開放は不要)
- 遊ぶ人に必要なもの: モダンブラウザだけ (Node.js やコマンド操作は不要)
- ゲーム本体 (Vite でビルドした静的ファイル) は、どこか 1 か所から https で配信する必要がある (配信先は未決定。「未決定事項」参照)。これは静的ファイルの置き場所で、通信には関わらない。招待リンクはこの配信先の URL になる

## ブラウザで対戦するときの制約

1. **ブラウザは接続を待ち受けられない**: Web ページの JavaScript は TCP/UDP ポートを開いて待ち受けられない。WebRTC は双方が同時に相手へ接続を試みる仕組み (ICE) なので、待ち受けなしで P2P 接続できる。ただし接続前に、互いの接続情報 (SDP: 暗号鍵の指紋、ICE の認証情報、接続先候補の IP とポート) を何らかの方法で交換する必要がある。方式 D ではこれを人間のコピペで行う
2. **NAT の種類によってはつながらない**: STUN で調べた「外から見た自分の IP・ポート」を教え合い、双方から同時に送って NAT に穴を開ける (ホールパンチ)。対称 NAT (宛先ごとにポートが変わる NAT) 同士などでは穴が開かず、TURN (中継) なしでは接続できない
3. **ブラウザはローカル IP を隠す**: Chrome・Firefox・Safari は、ローカル IP を含む接続先候補 (host 候補) を `xxxxxxxx.local` 形式のランダムな名前 (mDNS) に置き換える。同一 LAN なら名前解決できるので接続できるが、Tailscale などの仮想 LAN 越しには名前解決が届かず、仮想 LAN の IP は使えない
4. **タブがバックグラウンドに回ると止まる**: `requestAnimationFrame` が止まり、メインスレッドのタイマーは最大 1 秒間隔 (Chrome では 5 分後から 1 分間隔) に間引かれる。ホストのタブでレースを進めると、ホストが別タブに切り替えただけでレース全体が止まる (「ホストのタブがバックグラウンドに回ったときの対策」の節)

## 方式の比較

| 方式 | 構成 | 自前サーバー | インターネット越し | 通信品質 | 手間 |
| --- | --- | --- | --- | --- | --- |
| A. Node ホストサーバー + WebSocket | ホストが `npm run host` で Node プロセスを起動し TCP ポートで待ち受け、全員ブラウザから `ws://<ホストIP>:<ポート>` に接続 | 必要 (ホストの PC で Node を動かす) | ホストのポート開放が必要。キャリアグレード NAT では不可 | ○ LAN は問題なし。ロスが多いとカクつく (TCP) | 遊ぶ人: 大 (Node 導入・コマンド・ファイアウォール・ポート開放) / 開発: 小 |
| B. WebRTC DataChannel (A をシグナリングに使用) | A の WebSocket で接続情報だけ交換し、ゲームデータは WebRTC で送る | 必要 (A と同じ) | A と同じ条件 + STUN 依存 | ◎ | 遊ぶ人: 大 / 開発: 大 |
| C. デスクトップアプリ化 (Electron / Tauri) | アプリ本体がポートを開いて待ち受ける | 不要 (アプリが待ち受け) | ポート開放が必要 | ◎ UDP を直接使える | 遊ぶ人: 中 (インストール) / 開発: 大 (配布・パッケージング) |
| **D. ブラウザ同士の WebRTC、コードのコピペで接続 (採用)** | 招待リンク・返答コード (SDP を圧縮したもの) をチャットで手渡しし、ブラウザ同士が直接つながる | **不要** (公開 STUN のみ利用) | ポート開放不要。多くの家庭回線でつながるが、対称 NAT 等の組み合わせでは不可 | ◎ 状態は順序保証なし・再送なしで送れる | 遊ぶ人: 中 (1 人 1 往復のコピペ) / 開発: 中 |

### D を採用する理由

- **遊ぶ人がブラウザだけで完結する**: 招待リンクを開いて返答コードを送り返すだけ。Node の導入、コマンドの実行、ファイアウォールの許可ダイアログ、ルーターのポート開放がいらない
- **自前のサーバーを運用しない**: 常時動くサーバーの費用・保守・障害対応がない。使うのは公開 STUN (応答するだけの無料サービス) とゲーム本体の静的ファイル置き場だけ
- **インターネット越しでもポート開放がいらない**: A では必須だったポート開放が、キャリアグレード NAT のためにそもそもできない回線があった。D はホールパンチでつなぐので、多くの家庭回線 (IPv6 が使える回線を含む) で設定なしにつながる
- **通信品質がよい**: 車の状態を「順序保証なし・再送なし」で送れるので、TCP のようにロスした 1 パケットの再送待ちで後続が詰まることがない
- **外から勝手に接続されない**: 待ち受けるポートがなく、招待は 1 人 1 回限りなので、リンクを渡した相手以外は接続を試みることもできない

受け入れる弱点と対策:

| 弱点 | 対策 |
| --- | --- |
| コピペの手間 (8 人で 7 往復) | 招待リンク (開くだけで返答コードまで進む)、招待・返答の自動コピー、どこでも Ctrl+V で貼り付け、返答コードの自動振り分け、並行して発行、名前・チームの入力なし (「接続の手順」の節)。一度つながればロビーに戻っても接続を維持し、何レースでも続けて遊べる |
| 回線の組み合わせによってはつながらない (TURN なし) | 原因を見分けて案内し、「別の人がホストになる」などの回避策を示す |
| ホストのタブがバックグラウンドで止まる | ホストのレース進行を Web Worker で動かす。ホストに「タブを前面に」の注意を出す |
| 公開 STUN (第三者) に依存し、STUN サーバーにも IP が伝わる | STUN サーバーは 2 つ設定し、設定値は 1 か所 (`src/net/netConfig.ts`) にまとめて差し替え可能にする。同一 LAN なら STUN なしでもつながる |

### A を採用しない理由

- ホストに Node.js の導入と `npm run host` の実行を求めることになり、「ブラウザで遊ぶゲーム」として参加のハードルが高い
- インターネット越しではホストのポート開放が必須で、ルーター設定の知識が要るうえ、キャリアグレード NAT (一部の光回線・モバイル回線・マンション回線) ではそもそもできない。仮想 LAN ツールの導入を案内するしかなかった
- ポートを公開すると誰でも接続を試みられるため、パスワードや攻撃への備えが必要になる
- TCP のみで、ロス時にカクつく
- A の利点だった「ホストのタブに依存しない」は、D でもホストのレース進行を Web Worker に置くことで大部分をカバーできる (完全ではない。対策の節を参照)

B は A のサーバーが結局必要なので採用しない。C は配布とインストールの負担が大きく、ポート開放の問題も残るので採用しない。

## 全体構成

```
ホストのブラウザ (1 タブ)
┌──────────────────────────────────────────────────────┐
│ Web Worker (src/host/)                                 │
│  ・レース進行・判定 (カウントダウン、周回、順位、ゴール)  │
│  ・スナップショット生成 (30 回/秒)、ping (1 回/秒)、pong  │
│             ▲ postMessage (ArrayBuffer は転送)          │
│             ▼                                          │
│ メインスレッド                                          │
│  ・中継 (HostRelay): DataChannel ⇔ Worker (イベント駆動) │
│  ・RTCPeerConnection × 最大 7 (各 2 本の DataChannel)    │
│  ・ホスト本人のゲーム (自車の物理・描画)                 │
│    → Worker とは LocalTransport でつながる               │
└─────┬───────────────┬──────────────────────┬─────────┘
      │ DataChannel ×2 │                      │
      ▼               ▼                      ▼
  参加者 1 のブラウザ   参加者 2 ...            参加者 7

接続前だけ: 各ブラウザ ─(STUN 問い合わせ)→ 公開 STUN サーバー
接続情報:   ホスト ─招待リンク→ (チャット) → 参加者 ─返答コード→ (チャット) → ホスト
```

- 参加者同士は直接つながらない (星形)。接触の通知などはホストが中継する
- ホスト本人も「1 人の参加者」として、ネットワーク越しの参加者と同じメッセージ形式で Worker と話す (処理を 1 通りにできる。方式 A で `localhost` に接続していたのと同じ考え方)
- `RTCPeerConnection` は Worker では使えないので、メインスレッドに置く。メインスレッドは受信したものを Worker に渡すだけで、タイマーを持たない (バックグラウンドでの間引きの影響を受けない)
- ディレクトリ (実装済み):

| 場所 | 置くもの | DOM 依存 |
| --- | --- | --- |
| `src/shared/net/` | メッセージ定義 (`messages.ts`)、バージョンと上限値 (`protocol.ts`)、状態のバイナリ形式、招待・返答コードと招待リンクのエンコード/デコード (`connectionCode.ts`)、時刻合わせ、ホストの判定 (`HostRaceJudge`)、レース進行の数値 (`netRaceRules.ts`) | なし (Worker からも使う) |
| `src/host/` | ホストのブラウザでだけ動く部分: Worker の入口 (`hostWorker.ts`)、ホストのレース進行 (`RaceHost`)、中継 (`HostRelay`)、招待の発行と返答コードの受け付け (`HostLobby`) | Worker 側はなし、中継はメインスレッド |
| `src/net/` | 両方の役で使うブラウザ側の通信: `Transport` インターフェース、WebRTC 実装、`LocalTransport`、STUN と待ち時間の設定値 (`netConfig.ts`) | あり |
| `src/scenes/` | `MultiplayerScene` (ホスト / 参加の選択)、`HostLobbyScene`・`GuestLobbyScene` (ロビー)、`NetRaceScene`・`NetPauseScene`・`NetResultScene` (レース・ポーズ・リザルト) | あり |
| `src/ui/netTexts.ts` | 画面の案内文 (英語) | なし |

- Worker は Vite の `new Worker(new URL('./hostWorker.ts', import.meta.url), { type: 'module' })` 形式で読み込む (ビルドで別ファイルになる)
- 方式 A で予定していた `server/` ディレクトリと `npm run host` は作らない

## 接続の手順 (UI の流れ)

2026-09-26 に、ユーザーの要望「手順が長すぎる」を受けて短くした。方針は **中継サーバーは使わず 1 人 1 往復のコピペは残し、操作の数を減らす**。

### 全体の流れ

```
ホスト                                   参加者 (1 人ぶん)
─────────────────────────────           ─────────────────────────────
メニュー → MULTIPLAYER → ロビーを作る
(枠 1 の招待を自動で発行、1〜5 秒)
招待リンクを自動でコピー
(できなければ ENTER / クリックでコピー)
     └──── チャットで送る ─────────→  リンクを開く
                                        (タイトル・メニューを飛ばして参加画面へ。
                                         返答コードを自動で作る、1〜5 秒)
                                        返答コードを自動でコピー
                                        (できなければ ENTER / クリックでコピー)
     ┌──── チャットで送る ←─────────┘   「ホストの操作を待っています」(残り 120 秒)
どこでも Ctrl+V で返答コードを貼り付け
「接続中…」(最大 15 秒)
参加者一覧に追加される                  ロビーに入る (この時点で準備完了)
(次の人へは NEW INVITE → コピー)
START RACE
```

8 人なら、これを参加者 7 人ぶん行う (7 往復)。複数人ぶんは並行して進められる。

**手数** (チャットでのコピー・貼り付けの操作は数えない):

| 役 | 変更前 | 変更後 |
| --- | --- | --- |
| ホスト (参加者 1 人を呼んでスタートするまで) | キー 約 15 回 | キー 7 回 (自動コピーできないとき 8 回) |
| 参加者 | キー 約 11 回 | 招待リンクのクリック 1 回 (自動コピーできないとき 2 回) |

### 招待リンク

- 形式: `<origin + pathname>#join=PLO1I.…` (ゲームを配信しているページの URL + フラグメント)。中身は招待コード (「コードの形式と長さ」の節) そのもの。フラグメントはサーバーに送られないので、配信先に招待コードが渡ることはない
- リンクを開くと、タイトル・メニューを飛ばして参加画面 (`GuestLobbyScene`) に入り、返答コードの作成まで自動で進む
- 読み取ったらすぐ `history.replaceState` で URL からフラグメントを消す (再読み込みやブックマークで、使い終わった招待をもう一度使わないように)
- ゲームのタブを開いたままアドレス欄に招待リンクを貼った場合は、フラグメントだけが変わりページが読み込み直されないので、`hashchange` で招待リンクを見つけたらページを読み込み直す (ホスト中なら `beforeunload` の確認が出る)
- 返答コードはリンクにしない (ホストはすでにゲームの画面を開いているので、Ctrl+V で足りる)

### 貼り付けの受け付け (`extractConnectionCode`)

- 招待の貼り付け (参加者) は、招待リンクでも招待コードだけでも受け付ける。返答コードの貼り付け (ホスト) も同じ関数で読む
- 貼り付けた文字から `PLO…` のコードを取り出す。招待リンクなら `#join=` より後から探す (ページの URL に似た文字があっても取り違えない)
- 候補は 2 つ作る: (1) 空白・改行を除いてつないだもの (チャットの折り返しで切れたコード)、(2) 空白で区切ったもの (リンクの後ろに英単語が続く場合)。**チェックサムが合うほう** を使う。どちらも合わなければ最初の候補で読み、「コードが正しくありません」を出す

### 名前・チーム

- 入力を求めない。前回の値 (`localStorage`、保存できない環境では起動中だけ覚える) を使い、初回は `PLAYER` + 乱数 2 桁 (例: `PLAYER07`)。ロビーでいつでも変えられる (ホスト・参加者とも NAME / TEAM の項目)
- 参加者は、名前・チームの重なりで断られたら (`reject` の `nameTaken` / `teamTaken`)、自動で名前の末尾に数字を付ける・次の空いているチームに変えて入り直す。上限は **16 回**。超えたら断られた画面 (JOIN AGAIN、名前・チームの変更) を出す
- 自動で変えた値は保存しない (本人が変えたときだけ保存する)

### 準備完了とスタート

- 参加者は **ロビーに入った時点で準備完了**。READY の項目で外せる。入り直したとき・レース後にロビーへ戻ったときも準備完了に戻す
- ホストには READY がない。START RACE を押すと、ホスト本人の準備完了を自動で付けてから始める (全員の準備完了が届くのを最大 2 秒待つ)
- ホストのカーソル: 参加者が入っていて、待っている招待 (招待中・接続中の枠) がなければ START RACE に移す。リザルトからロビーに戻ったときも START RACE に置く

### 画面上部の「いま何をすればよいか」

- ホスト・参加者とも、画面の上に次の操作を 1 行 (最大 64 文字、英語) で出す

| 画面 | 状態 | 表示 |
| --- | --- | --- |
| ホスト | 招待を作っている | `PREPARING AN INVITE LINK... (UP TO 5 SEC)` |
| ホスト | 招待ができて、まだコピーしていない | `PRESS ENTER (OR CLICK) TO COPY THE INVITE LINK` |
| ホスト | 接続中の枠がある | `CONNECTING TO A PLAYER... (UP TO 15 SEC)` |
| ホスト | 招待中の枠がある | `SEND THE LINK TO A FRIEND, THEN PASTE THEIR REPLY HERE (CTRL+V)` |
| ホスト | 参加者がいて全員準備完了 / まだの人がいる | `START THE RACE, OR MAKE A NEW INVITE FOR MORE PLAYERS` / `WAITING FOR ALL PLAYERS TO BE READY` |
| ホスト | 誰もいない | `SELECT "NEW INVITE" TO INVITE A FRIEND` |
| 参加者 | ロビーで準備完了 / 外している | `YOU ARE READY. WAIT FOR THE HOST TO START THE RACE.` / `SET "READY" TO YES WHEN YOU ARE READY.` |

- 参加者のそのほかの段階 (貼り付け待ち、返答コードの作成中、コピー待ち、ホスト待ち、失敗) も同じ行に出す。文言は `GuestLobbyScene` の実装に従う

| 自動の招待 | ロビーを作った直後に枠 1 の招待を自動で発行し、できたら自動でコピーを試す |

| 参加者一覧 | 8 枠。枠 0 はホスト本人。枠 1〜7 の状態: `OPEN` (空き) / `PREPARING LINK...` / `INVITED <残り時間>` / `CONNECTING...` / 参加済み (名前・チーム色・準備状態・接続経路 LAN/NET・往復遅延 ms) / `FAILED: <理由>`。**招待の有効期限の残りはこの一覧にだけ出す**。行をクリックするとその枠を表示する |
| 招待リンク欄 | 表示中の枠のリンク (読み取り専用の DOM のテキスト欄)、[COPY] [CANCEL] ボタン。コピー前は大きな「PRESS ENTER (OR CLICK) / TO COPY THE INVITE LINK (SLOT n)」、コピー後は「SLOT n: INVITE LINK COPIED / SEND IT TO ONE FRIEND. CLICK HERE TO COPY AGAIN.」 |
| IP アドレスの注意 | 招待リンク欄の真下に常に出す (リンク用の文言。「セキュリティと注意」の節)。STUN の応答なし・対称 NAT の疑いの警告はその下 |
| 返答コードの貼り付け | 画面のどこでも Ctrl+V。PASTE REPLY の項目 (クリップボードから読む) と貼り付け欄もある。どの枠への返答かはコードの中身で自動判別するので、貼り付け先を選ぶ必要はない |
| CANCEL | 招待中・失敗の枠を空きに戻す (発行済みの招待は無効になる) |
| 失敗の枠 | 理由と案内文、[COPY DETAILS] |
| ホスト設定 | 周回数 (LAPS)。コースはコース 1 固定 (パスワードは不要。招待が 1 人 1 回限りのため) |
| 注意 | 「レース中はこのタブを閉じたり再読み込みしないでください」(「ホストのタブがバックグラウンドに回ったときの対策」の節) |
| CLOSE LOBBY | 参加者がいるときは 2 回押し (3 秒以内)。全員に `hostClosed` を送り、MULTIPLAYER の画面に戻る |

### 参加者の画面 (ロビーに参加)

| 段階 | メニュー | 内容 |
| --- | --- | --- |
| 貼り付け待ち (メニューから入ったとき) | PASTE INVITE / NAME / TEAM / BACK | 画面のどこでも Ctrl+V、PASTE INVITE、貼り付け欄。貼り付けた瞬間に形式・バージョンを確認する。招待リンクで開いた場合はこの段階を飛ばす |
| 返答コードの作成中 | BACK | 最大 5 秒 |
| ホスト待ち | COPY REPLY CODE / NAME / TEAM / START OVER / BACK | 返答コード (読み取り専用の DOM のテキスト欄)。できた時点で自動でコピーを試し、できなければ大きな「PRESS ENTER (OR CLICK) TO COPY …」。**IP アドレスの注意 (コード用の文言) をコピー欄の真下に常に出す**。「ホストの操作を待っています」と残り時間 |
| 接続後の応答待ち | BACK | `welcome` を最大 5 秒待つ |
| ロビー | READY / NAME / TEAM / LEAVE LOBBY | ホストと同じ参加者一覧 (ホストから `lobby` で届く)。入った時点で準備完了 |
| 断られた | JOIN AGAIN / NAME / TEAM / LEAVE LOBBY | 自動の入り直し (16 回) で解決しなかったとき、またはレース中・満員など |
| 失敗 | COPY DETAILS / START OVER / BACK | 原因ごとの案内文 |
| 切断 | OK | ホストとの接続が切れた |

- START OVER は最初 (招待の貼り付け) に戻る。1 つの招待は 1 回しか使えないので、ホスト待ち以降にもう一度招待を貼った場合は「START OVER してから」と案内する
- Canvas にはテキスト入力がないので、コードの表示・貼り付けは `paste` イベント (`clipboardData`) と `navigator.clipboard` を使う。コピーできない環境 (権限の拒否など) のために、コードを選択できる表示 (DOM の読み取り専用テキスト欄を Canvas に重ねる) も用意する。見た目は art-director が決める
- 自動コピーは、ページにフォーカスがあるなどブラウザが許す場合だけ成功する。失敗しても知らせず、「ENTER でコピー」の大きな案内を出したままにする (ENTER・クリックはユーザー操作なのでコピーできる)
- `navigator.clipboard` は安全なコンテキスト (https または `localhost`) でのみ使えるので、ゲーム本体は https で配信する

### 案内文の言語

- 画面の案内文はすべて英語 (`src/ui/netTexts.ts`)。HUD のビットマップフォントが英大文字・数字・記号だけのため。この文書の日本語の案内文は意味の原文で、画面にはその英訳を出す
- 画面の文言では「INVITE CODE」を使わず「INVITE LINK」とする (2026-09-26)

### 手間を減らす工夫

1. **ICE 候補を集め終えてからコードを出す (non-trickle)**: 通常の WebRTC は接続先候補を後から小出しに送る (trickle) が、コピペでは往復が増えるので、候補の収集 (`iceGatheringState` が `complete`) を待ってから 1 本のコードにまとめる。収集は最大 **5 秒** で打ち切り、それまでに集まった候補で出す (STUN が応答しない場合に長く待たせないため)
2. **コードを短くする**: SDP 全文 (500〜1,500 文字) をそのまま渡さず、接続に必要な値だけを取り出してバイナリに詰め、Base64url (URL やチャットで崩れない `A-Z a-z 0-9 - _` のみ) にする。受け取った側は固定のひな形に値を埋めて SDP を組み立て直す (詳細は次節)
3. **招待リンク**: 参加者はリンクを開くだけで返答コードまで進む。メニュー操作・貼り付けがいらない
4. **自動コピーと、どこでも貼り付け**: 招待リンク・返答コードはできた時点で自動でコピーを試し、できなければ ENTER かクリック 1 回でコピーする。貼り付けは入力欄を選ばなくても Ctrl+V で受け付け、コードの種類 (招待 / 返答) も自動判別する
5. **返答コードの自動振り分けと並行発行**: ホストは招待を枠ごとに先にまとめて発行し、全員に一斉に送れる。返答コードには枠番号とロビー ID が入っているので、届いた順に同じ場所へ貼り付けるだけでよい
6. **入力の省略**: 名前・チームは前回の値、参加者の準備完了は自動、ホストの READY はなし
7. **一度つながれば維持する**: レースが終わってロビーに戻っても接続は切らない。同じメンバーなら何レースでも続けて遊べ、コピペはセッションの最初だけで済む。コードの再利用 (次回の起動時に同じコードで入る) はできない (WebRTC の認証情報が接続ごとに使い捨てのため)

### 1 本のコードで複数人を受け付けられないか (検討)

| 案 | 内容 | 評価 |
| --- | --- | --- |
| 1 つの招待を複数人で使う | 1 つの offer (招待) に複数人が answer (返答) する | **不可**。WebRTC の 1 つの接続 (`RTCPeerConnection`) は 1 対 1 で、offer の ICE 認証情報・暗号鍵の指紋も 1 つの接続に結びつく |
| まとめ招待コード | 7 人ぶんの offer を 1 本に詰め、参加者は自分の枠番号を選んで返答する | 可能だが**採用しない**。長さは約 7 倍 (約 800 文字) になり、枠番号の重複 (2 人が同じ枠を選ぶ) の扱いが要る。返答コードは結局 7 本必要なので、減るのはホストの「コピー」操作だけ。個別の招待リンクをまとめて発行してチャットに並べて貼るのと手間がほぼ同じ |
| 参加者同士の中継 | つながった参加者経由で次の人の接続情報を渡す | 不可。まだ誰ともつながっていない人には、コピペ以外に情報を渡す経路がない |
| 返答を中継サーバーで自動で返す | 返答コードのコピペをなくす | **採用しない** (2026-09-26)。自前のサーバーを立てない方針に反する。1 往復は残し、操作を減らす方向で対応した |

結論: **1 人 1 往復の個別コード + 招待リンク + 並行発行 + 自動振り分け** とする。

### コードの形式と長さ

```
PLO1I.<Base64url>   招待コード (Invite)。招待リンクの #join= の後ろに入れて渡す
PLO1R.<Base64url>   返答コード (Reply)
```

- 先頭の `PLO` はゲーム名、`1` はコード形式のバージョン (`codeFormatVersion`)、`I` / `R` は種類。チャットで改行や空白が混ざっても読めるようにする (「貼り付けの受け付け」の節)
- 中身 (バイナリ、多バイトはビッグエンディアン):

| 項目 | バイト数 | 招待 | 返答 | 備考 |
| --- | --- | --- | --- | --- |
| プロトコルのバージョン | 2 | ○ | ○ | `protocolVersion` = `netFormatVersion` × 1000 + `physicsVersion` (いま **1003** = 形式 1・物理 3)。通信の形式と物理の両方が一致しないと一緒に走れないので 1 つの番号にまとめた。違えば貼り付けた時点で拒否 |
| ロビー ID | 4 | ○ | ○ | ホストがロビー作成時に乱数で作る。別のロビーへの返答を見分ける |
| 枠番号 | 1 | ○ | ○ | 1〜7 |
| フラグ | 1 | ○ | ○ | STUN の応答なし、対称 NAT の疑い、SDP 全文形式 (下記) |
| ICE ufrag | 1 + 4〜32 | ○ | ○ | 長さ + 文字列 (Chrome は 4 文字) |
| ICE pwd | 1 + 22〜32 | ○ | ○ | 長さ + 文字列 |
| DTLS 指紋 (SHA-256) | 32 | ○ | ○ | 暗号化の相手確認に使う。これが一致しない相手とはつながらない |
| 接続先候補 | 1 + 候補ごと 7〜19 | ○ | ○ | 候補数 + [種類 1 (host/srflx、IPv4/IPv6/mDNS) + アドレス (IPv4 は 4、IPv6 と mDNS の UUID は 16) + ポート 2]。UDP のみ、最大 6 個 |
| チェックサム | 2 | ○ | ○ | CRC-16。コピー漏れ (途中で切れた) を検出する |

- 固定の値は入れない (ひな形側に持つ): `m=application ... webrtc-datachannel`、`a=setup` (招待は `actpass`、返答は `active`)、`a=mid:0`、`a=sctp-port:5000`、`a=max-message-size`、候補の優先度と foundation (種類から決める)
- 名前・チームなどはコードに入れず、接続後に `join` で送る (コードを短く保つ)
- **長さの目安**: 候補 2〜4 個 (mDNS の host 候補 + IPv4 の srflx 候補 + IPv6 の候補) で 約 100〜170 バイト → **約 140〜230 文字** (招待リンクはこれにページの URL が付く)。上限の目安は 300 文字 (チャットの 1 メッセージに収まり、目で見ても「長い 1 行」程度)
- 汎用の圧縮 (deflate) は、この大きさでは中身の大半が乱数 (認証情報・指紋) のためほとんど縮まないので使わない。ただし、SDP が想定外の形 (ブラウザの仕様変更など) で値を取り出せなかった場合だけ、フラグを立てて **SDP 全文を deflate 圧縮 + Base64url** で入れる (約 500〜1,000 文字。長いがつながる)
- エンコード・デコードは DOM に依存しない純粋な関数として `src/shared/net/connectionCode.ts` に置く

## Transport の設計

ゲーム側 (シーン、ホストのレース進行) は `Transport` インターフェース越しに通信し、WebRTC を直接触らない。

### インターフェース

参加者側 `ClientTransport`:

| メンバー | 内容 |
| --- | --- |
| `sendState(data: ArrayBuffer)` | 状態を送る (届かなくてよい) |
| `sendEvent(msg)` | イベントを送る (必ず順番どおり届く) |
| `onState` / `onEvent` | 受信時に呼ばれる |
| `onClose(reason)` | 切断時に呼ばれる (`hostClosed` / `connectionFailed` / `timeout`) |
| `close()` | 切断する |
| `stats` | 往復遅延 (ms)、接続経路 (`lan` / `internet`) |

ホスト側 `HostTransport` (Worker 内で使う):

| メンバー | 内容 |
| --- | --- |
| `sendState(peerId, data)` / `broadcastState(data)` | 状態を 1 人 / 全員に送る |
| `sendEvent(peerId, msg)` / `broadcastEvent(msg)` | イベントを 1 人 / 全員に送る |
| `onPeerJoin(peerId)` / `onPeerLeave(peerId, reason)` | 参加・離脱 |
| `onState(peerId, data)` / `onEvent(peerId, msg)` | 受信 |
| `kick(peerId, reason)` | 切断する (不正なメッセージなど) |

実装:

| 実装 | 使う場所 | 中身 |
| --- | --- | --- |
| `WebRtcClientTransport` | 参加者 | `RTCPeerConnection` 1 つ + DataChannel 2 本 |
| `LocalTransport` | ホスト本人のゲーム | Worker と `MessagePort` でつなぐ。遅延ほぼ 0 |
| `WorkerHostTransport` | ホストの Worker | メインスレッドの `HostRelay` と `postMessage` でやりとりし、`HostRelay` が各参加者の DataChannel に振り分ける |
| `LoopbackTransport` | 開発・確認用 | 1 つのタブの中で疑似的に複数人をつなぐ。遅延・ロスを擬似的に入れられるようにする |

### DataChannel は 2 本

| チャンネル | 設定 | 流すもの | 形式 |
| --- | --- | --- | --- |
| `state` | `ordered: false`, `maxRetransmits: 0` (順序保証なし・再送なし) | `carState`、`snapshot`、`ping` / `pong` | バイナリ |
| `event` | `ordered: true`、再送あり (既定) | それ以外すべて (`join`、`lobby`、`raceStart`、`raceEvent`、`collision`、`result`、`hostClosed` など) | JSON 文字列 |

- 2 本とも `negotiated: true` と固定の `id` (`state` = 0、`event` = 1) で両側が作る。相手側の `ondatachannel` を待つ必要がなく、コードにチャンネル情報を入れなくてよい
- `binaryType = 'arraybuffer'`
- `state` の 1 メッセージは **1,000 バイト以下** にする。大きいと内部で分割され、1 片でも失うと全体が失われる (8 台ぶんのスナップショットは 約 250 バイトで収まる)
- 状態は古いものに価値がないので、各メッセージに連番を付け、受信側は最新より古い連番を捨てる (順序保証なしのため)。**連番は `Transport` が送信時に書き込む** (送る側のゲームの処理は連番を気にしない)
- `ping` / `pong` を `state` に流すのは、再送による遅れが遅延の測定値に混ざらないようにするため。失われた `ping` は数えない
- 送信が詰まったとき: `state` は `bufferedAmount` が 16KB を超えていたらその回の送信を捨てる。`event` は捨てない
- `collision` は再送ありの `event` で送る (取りこぼすと接触が片側だけになるため)。受信時に、接触時刻から 250ms 以上経っていたら適用しない (遅れて届いた衝撃で急に弾かれるのを防ぐ)
- 受信サイズの上限: `state` 1,000 バイト、`event` 16KB。超えたら切断 (「ホストによる判定と不正対策」)

## ホストのタブがバックグラウンドに回ったときの対策

### 何が起きるか

| 場所 | バックグラウンドでの挙動 |
| --- | --- |
| `requestAnimationFrame` | 止まる |
| メインスレッドの `setTimeout` / `setInterval` | 最大 1 秒に 1 回に間引かれる。Chrome は隠れて 5 分後から 1 分に 1 回 |
| DataChannel・`postMessage` の受信処理 | 届いたときに実行される (タイマーではないので間引かれない) |
| 専用 Web Worker のタイマー | 間引かれない (主要ブラウザの現状の挙動。仕様で保証されたものではないので、実機で確認する) |
| タブの凍結 (省メモリ機能など) | WebRTC 接続があるタブは対象外とされるが、ブラウザとバージョンに依存するので頼らない |

### 方針

1. **ホストのレース進行・判定は Web Worker で動かす**: カウントダウン、周回・チェックポイント判定、順位、ゴール、不正チェック、スナップショット生成 (30 回/秒)、`ping` (1 回/秒) と `pong` は Worker の中で行う。ホストのタブが隠れてもレースは止まらない
2. **メインスレッドはイベント駆動の中継だけ**: DataChannel で受けたものを Worker に渡し、Worker から来たものを DataChannel に送る。タイマーを使わないので間引きの影響を受けない
3. **ホストの時刻**: Worker の `performance.timeOrigin + performance.now()` をホスト時刻とする (メインスレッドとは基準が違うので混ぜない)
4. **ホスト本人の車**: ホスト本人の車の物理と描画はメインスレッドで動くので、タブが隠れると止まる。これは参加者がタブを隠した場合と同じ扱いにする (次項)
5. **車の状態が届かない車の扱い (ホスト本人も参加者も同じ規則)**:

| 状態が届かない時間 | 扱い |
| --- | --- |
| 3 秒 | その場で止まったまま **ゴースト (すり抜け)** にする (game-design.md 7.10 節のゴーストと同じ: 当たり判定なし)。他の車がぶつからないようにするため。状態が再び届けば通常に戻る (戻るときは 7.10 節の「重なっている間は延長」に従う)。**最後に受け付けた (検証を通った) 状態から数える** (不正として捨てた状態を送り続けても延びない) |
| 60 秒 | リタイア扱い (`raceEvent`)。接続は切らず、ロビーに戻れば次のレースに出られる。**最後に状態を受信した時刻から数える** |

6. **ロビーでは切断しない**: 生存確認は `ping` / `pong` で行う。`ping` は双方向 (ホストの Worker も参加者も送る) で、相手の `ping` には受け取った側がすぐ `pong` を返す (ホスト側は Worker が返す。Worker のタイマーは間引かれない)。ロビーで何分タブを離れても切れない
7. **ホストへの注意表示**:
   - ロビー (ホストの画面、常時): 「ホストへ: レース中はこのタブを閉じたり再読み込みしないでください。別のタブに切り替えてもレースは続きますが、あなたの車は止まります」
   - レース開始時 (ホストだけ、メッセージ帯で 3 秒): 「ホストはこのタブを前面にしたままにしてください」
   - タブが前面に戻ったとき、隠れていた時間が 3 秒以上ならメッセージ帯で「タブが裏に回っていたため、車が止まっていました」
   - ホストがタブを閉じる・再読み込みしようとしたら、参加者がいる間は `beforeunload` で確認ダイアログを出す
   - パソコンのスリープでは全員の接続が切れる (防げない)。ロビーの注意書きには含めず、操作説明 (HelpScene) に書く

## 接続できなかったときの扱い

### 待ち時間の上限

| 段階 | 上限 | 超えたら |
| --- | --- | --- |
| 接続先候補の収集 (招待・返答コードを作るとき) | 5 秒 | 集まった候補でコードを出す。srflx 候補が 1 つもなければ「STUN の応答なし」フラグを立てる |
| 招待の有効期限 (ホスト) | 10 分 | 枠を「失敗 (期限切れ)」にする。後から返答コードが来たら期限切れと表示 (NAT の対応付けが時間で消え、つながらなくなるため) |
| 返答コードを出してからホストが貼り付けるまで (参加者) | 画面の残り時間は 120 秒。接続の打ち切りは **合計 135 秒** (120 + ホストが貼ってからの 15 秒) | 参加者に「時間切れ。新しい招待リンクをもらってください」を表示する。120 秒ぎりぎりに貼られた場合もつながるよう、接続そのものは 15 秒長く待つ |
| ホストが返答コードを貼ってから接続完了まで (ICE 確認 → DataChannel 2 本が開く) | 15 秒 | 「失敗」として原因を判定する |
| DataChannel が開いてから `join` / `welcome` まで | 5 秒 | ホスト: `join` しない相手を切断する。参加者: 「接続後の応答がありません」 |

### 原因の見分け

| 状況 | 見分け方 | 案内文 (ホスト / 参加者の画面) |
| --- | --- | --- |
| コードが壊れている | 先頭が `PLO` でない、Base64url として読めない、チェックサムが合わない | 「コードが正しくありません。途中で切れていないか確かめて、もう一度コピーしてください」 |
| 種類が違う | 参加者が返答コード (`R`) を、ホストが招待リンク・コード (`I`) を貼った | 「これは返答コードです。ホストから届いた招待リンクを貼り付けてください」/「これは招待リンクです。参加者から届いた返答コードを貼り付けてください」 |
| バージョン違い | プロトコルのバージョンが違う | 「ゲームのバージョンが違います。全員ページを再読み込みして最新にしてください」 |
| 別のロビー・使用済み・期限切れ | ロビー ID が違う / 枠がすでに参加済み / 期限切れ | 「このロビーへの返答コードではありません」/「この枠はすでに使われています」/「期限切れです。新しい招待を作ってリンクを送ってください」 |
| STUN に届かない | 自分の候補に srflx がない (コードのフラグで相手の状態も分かる) | コード発行時に警告: 「インターネット越しの接続情報を取得できませんでした。同じ LAN の相手とだけ接続できます (UDP 通信が制限されたネットワークの可能性があります)」 |
| 対称 NAT の疑い | 2 つの STUN サーバーから得た srflx 候補が、同じ元ポートに対して違うポートになっている | コード発行時に注意: 「あなたの回線は接続しにくい種類かもしれません。つながらない場合は、別の人にホストを代わってもらってください」 |
| 接続の確立に失敗 (ICE の失敗) | `iceConnectionState` / `connectionState` が `failed`、または時間内に `connected` にならない | 下記の「つながらなかったとき」の案内 |
| 同じ LAN にいるのに失敗 | 双方の srflx の IP が同じ (同じルーターの内側) なのに ICE が失敗。診断の記録の `isSamePublicAddress` で判定する | 「つながらなかったとき」の案内の代わりに: 「同じネットワークにいるようですが接続できませんでした。ゲスト用 Wi-Fi など、端末同士の通信を禁止しているネットワークでは遊べません。別のネットワークに切り替えてください」 |
| つながった後の応答なし | DataChannel が開いたのに 5 秒以内に `welcome` / `join` が来ない | 「接続後の応答がありません。ページを再読み込みしてやり直してください」 |

**つながらなかったとき** の案内文 (ホスト・参加者の両方に表示):

> 接続できませんでした。
> お互いの回線の組み合わせ (対称 NAT、キャリアグレード NAT、厳しいファイアウォールなど) によっては、この方式ではつながらないことがあります。次を試してください。
> 1. もう一度やり直す (新しい招待リンクで)
> 2. 別の人にホストを代わってもらう
> 3. どちらかがスマートフォンのテザリングなど、別の回線を使う
> 4. 同じ LAN (同じ Wi-Fi) で遊ぶ

- 失敗した枠 (ホスト) と失敗の画面 (参加者) には [COPY DETAILS] を付け、原因の調査用に状態の記録 (候補の種類と数、ICE の状態の移り変わり、フラグ、経過時間、`isSamePublicAddress`) をコピーできるようにする。**IP アドレスは記録に含めない** (`isSamePublicAddress` は同じかどうかの真偽値だけ)
- 仮想 LAN (Tailscale など) はこの方式では回避策にならない (ブラウザがローカル IP を隠すため) ので、案内に含めない

### 同一 LAN の場合

- 同一 LAN では mDNS の host 候補同士で直接つながるので、**STUN に届かなくても (インターネットにつながっていなくても) 接続できる**。STUN の応答がなくてもエラーにはせず、上記の警告だけを出してコードを発行する
- 参加者一覧の接続経路は、実際に使われている候補の組 (`getStats` の選ばれた候補ペア) が host 同士なら `LAN`、それ以外なら `NET` と表示する。5 秒ごとに調べ直す

### 使う STUN サーバー

- `stun:stun.l.google.com:19302` と `stun:stun.cloudflare.com:3478` の 2 つ (対称 NAT の判定に 2 つ必要)
- 設定値は `src/net/netConfig.ts` の 1 か所にまとめ、差し替えられるようにする
- IPv6 の srflx 候補も使う。IPv4 がキャリアグレード NAT でも IPv6 が使える回線 (国内の IPoE 回線に多い) なら、IPv6 で直接つながることが多い

## セキュリティと注意

### コードに IP アドレスが含まれる

- 招待リンク・返答コードには、**その人の回線のグローバル IP アドレス** (srflx 候補) が含まれる。ブラウザがローカル IP を隠す設定になっていない場合は LAN の IP も含まれる
- コピー欄の真下に、常に次の注意書きを出す。ホストはリンク用、参加者はコード用の文言にする:

> このリンク (コード) には、あなたのインターネット回線の IP アドレスが含まれます。一緒に遊ぶ信頼できる相手にだけ、個別に (DM などで) 渡してください。SNS や公開の場所には貼らないでください。

- 招待は 1 人 1 回限りで、使った後や期限切れ後は誰も接続に使えない。ただし IP アドレスが見えることには変わりないので、注意書きは常に出す
- 招待リンクのフラグメント (`#join=…`) はブラウザからサーバーに送られないので、ゲームの配信先のログに招待コードは残らない。開いた側ではすぐ URL から消す (「招待リンク」の節)
- STUN サーバー (Google、Cloudflare) にも、問い合わせのときにグローバル IP が伝わる。操作説明に記載する

### 通信の保護

- DataChannel は DTLS で必ず暗号化される。コードに入っている暗号鍵の指紋と一致する相手としかつながらないので、リンク・コードを渡した相手以外が割り込むことはできない (コードを受け渡すチャットが信頼できる前提)
- 待ち受けるポートがないので、外部から接続を試みられることはない。方式 A で予定していた参加パスワードは不要

### ホストの権限

- レース進行と判定 (スタート時刻、フライング、周回・チェックポイント、順位、ゴール、ペナルティ、リタイア) はすべてホストが行い、参加者はホストの判定に従う
- ホストのブラウザでは判定を書き換えることも技術的には可能。「知り合い同士で遊ぶ」前提として、ホスト自身の不正は防がない
- ホストは参加者からの受信を検証する (「ホストによる判定と不正対策」)。参加者もホストからの受信について、サイズ上限と形式のチェックだけは行い、壊れたものは捨てる。スナップショットの他車の速さは 1,200 px/秒、受け取った `collision` の衝撃は 1,100 px/秒に丸める (壊れた値で接触の計算が暴れないように)

## 同期方式

レースゲームでは車同士が絡む時間が短く、操作の即応性が最重要なので、次の分担にする。

| 対象 | 担当 | 理由 |
| --- | --- | --- |
| 自分の車の挙動 | 各クライアント (自分で計算) | 入力遅延ゼロで操作できる。ホスト側で全車を計算すると、ホストから遠い人ほど操作が遅れる |
| 他の車の表示 | 受け取った位置を補間して描画 | 100ms 過去の状態を 2 点間で補間し、なめらかに見せる |
| レース進行 (カウントダウン、周回、順位、ゴール、失格) | ホスト (Worker) | 全員で結果を一致させ、不正を防ぐ |
| 車同士の接触 | 各クライアントが自分の車の反応を計算し、ホストが仲介して相手にも伝える | 詳細は「車同士の接触」の節 |

「クライアント」はホスト本人を含む全プレイヤーのゲーム画面を指す (ホスト本人は `LocalTransport` で Worker とつながる)。マルチでは CPU 車は出さない。

### 送信内容と頻度

- クライアント → ホスト: 自分の車の状態 (位置、向き、速度、通過したチェックポイント、状態の時刻) を **毎秒 30 回** (`state` チャンネル)
- ホスト → 全員: 全車の状態をまとめたもの (スナップショット) を **毎秒 30 回** (`state` チャンネル、Worker のタイマーで送る)。各車の状態は、状態の時刻からスナップショットの時刻まで最大 100ms 進めて送る
- 状態データはバイナリ (`ArrayBuffer` + `DataView`、1 台あたり 20〜30 バイト程度 + 連番) で送る。ロビーやイベントなど頻度の低いメッセージは JSON (`event` チャンネル)
- 目安の通信量: 8 台 × 30 バイト × 30 回/秒 ≒ 7KB/秒 (ホストの送信はこれ × 7 人)。家庭回線で問題にならない
- ロビーでは、ホストが参加者一覧 (往復遅延・接続経路を含む) を 2 秒ごとに送り直す

### メッセージ一覧

| 方向 | 種類 | チャンネル | 内容 |
| --- | --- | --- | --- |
| C→H | `join` | event | プレイヤー名 (英大文字と数字 3〜8 文字)、チーム (車番 1〜8)、プロトコルのバージョン |
| H→C | `welcome` / `reject` | event | 割り当てたプレイヤー ID (= 枠番号)、参加者一覧、設定 / 拒否理由 (`full` 満員、`version` バージョン違い、`nameTaken` / `teamTaken` 名前・チームの重複、`invalidName` 名前の規則違反、`raceInProgress` レース中)。`reject` を送ってから 1 秒後に切断する (先に `reject` が届くように) |
| H→全 | `lobby` | event | 参加者一覧 (名前、チーム、準備状態、スタートタイヤ、接続経路、往復遅延)、設定 (コース、コースのバージョン、周回数) |
| C→H | `ready` | event | 準備完了の有無、スタートタイヤ。参加者はロビーに入った時点で自動で送る。ホスト本人は START RACE のときに送る |
| H→全 | `raceStart` | event | セッションの種類、スタート (消灯) の時刻 `startTime` (ホスト時刻)、設定、グリッド順のプレイヤー ID、乱数の種 `seed` (「スタートの時刻表」の節) |
| C→H | `carState` | state | 自分の車の状態 (バイナリ、連番付き) |
| H→全 | `snapshot` | state | 全車の状態 (バイナリ、連番付き) |
| H→全 | `raceEvent` | event | 周回通過、ゴール、失格、リタイア、ゴースト化 / 解除、切断、ペナルティ |
| H→全 | `result` | event | 最終順位とタイム |
| C→H→C | `collision` | event | 接触相手の ID、衝撃の向きと大きさ、時刻、スピンの向き (ホストが相手に中継) |
| H→全 | `hostClosed` | event | ホストが終了することの通知 |
| 双方向 | `ping` / `pong` | state | 遅延測定と時刻合わせ、生存確認。**ホストの Worker も参加者も `ping` を送り**、受けた側が `pong` を返す (参加者の `ping` にはホストの Worker が答える)。間隔は 1 回/秒。参加者は接続直後に 100ms 間隔で 10 回送り、時刻合わせを早く収束させる |

### スタートの時刻表

- ホストは START RACE で `raceStart` を送る。`raceStart` は **グリッドに並ぶ時刻の 1.5 秒前** に届くように送る (全員に届くまでの余裕)
- `raceStart` に入れるのは消灯の時刻 `startTime` と `seed` だけで、グリッド・ランプ点灯の時刻は各自が同じ計算で求める (`raceStartSchedule`):
  - 5 つ点灯してから消灯までの待ち (0.5〜2.5 秒の一様乱数) は `seed` から決めるので全員で一致する
  - グリッドに並ぶ時刻 = `startTime` − (1 つ目の点灯までの時間 + 点灯の間隔 × 4 + 消灯までの待ち)。ランプの時間は game-design.md 7.2 節
- グリッド順は `seed` の乱数順 (マルチには予選がないため。M3 の予選を入れるまで)
- 各クライアントは自分のシミュレーション時刻をホスト時刻に合わせて進め (「時刻合わせ」の節)、スタートランプ・消灯を同時に迎える

### フライング

- 正規の操作では消灯まで車は動けない (game-design.md 7.2 節: 消灯までグリッドに固定)
- ホストは改造したクライアントへの備えとして、消灯前の位置から判定する: 消灯前に **グリッドの位置から 5 px 以上離れた**、または **止まった状態から消灯後の経過時間では届かない距離** にいたらフライング (ペナルティは game-design.md 7.2 節)
- 消灯前に接触を「受けた」車 (ホストが `collision` を中継した相手) は判定しない (押されて動いただけのため)

### 車同士の接触

各車は持ち主のクライアントが計算しているため、接触は次の方法で処理する。

1. **近くの車は予測位置で扱う**: 他車は通常 100ms 過去の位置を補間して表示するが、それでは当たり判定がずれる。自分の車から車 3 台分 (114 px) 以内の他車は、最新の位置と速度から「今の位置」を予測して表示・判定に使う (予測で進める時間は最大 250ms)
2. **自分の車だけ動かす**: 重なりを検出したら、自分の車を押し戻し、相対速度と重さ (全車同じ) から計算した衝撃を自分の速度に加える
3. **相手にも伝える**: 接触したクライアントはホストに `collision` (相手 ID、衝撃の向きと大きさ、時刻) を送り、ホストが相手に中継する。相手がまだ接触を検出していなければ、受け取った衝撃を自分の車に適用する (接触時刻から 250ms 以上経っていれば適用しない)
4. **二重適用を防ぐ**: 同じ 2 台の組み合わせで短時間 (例: 200ms) 内に 2 回目の衝撃は適用しない

- 遅延が大きい相手ほど、接触の見た目にずれが出る (相手との遅延が 100ms を超えると目立つ)。参加者同士の通信はホスト経由なので、実際の遅延は「自分 → ホスト → 相手」の合計になる。LAN・国内の通信であれば許容範囲の想定
- ホストの不正チェックは、接触による急な速度変化を誤検出しないよう、接触を受けた車の判定を緩める (「ホストによる判定と不正対策」)
- 衝撃の強さ、押し戻し量、スピンの条件は `docs/design/car-physics.md` の「9. 接触 (衝撃)」で決めている (当てた側の判定は両クライアントで同じ式になるので結果が一致する)

### 切断時の扱い

**ホストが抜けた場合 (レース終了)**

- ホストが終了操作をした場合 (ロビーの CLOSE LOBBY、レース中のポーズの CLOSE LOBBY): 全員に `hostClosed` を送ってから接続を閉じる。参加者がいるときは 2 回押し。レース中は全員のレースが終わる
- ホストがタブを閉じた・再読み込みした場合: `pagehide` で `hostClosed` を送ってから閉じる (届かないこともあるので、下の検出が最終手段)
- 異常終了・回線切断の場合: クライアントは DataChannel の `close`、`connectionState` の `failed`、または **3 秒間 `snapshot` が届かない** ことで検出する (`disconnected` は一時的に回復することがあるので、それだけでは切断としない)
- どの場合もクライアントはレースを止めて「ホストとの接続が切れました。レースを終了します」と表示し、OK でタイトル画面に戻る
- 結果は記録しない (レースは無効)
- 各参加者はホストとしかつながっていないので、ホストの代わりを立てて続けることはしない

**クライアントが抜けた場合 (レース続行)**

- 参加者のポーズには RETIRE がある (ホストは RETIRE の代わりに CLOSE LOBBY)。2 回押しで、接続を切ってメニューに戻る。もう一度入るには新しい招待が要る
- ロビーの LEAVE LOBBY も同じく接続を切る
- 検出: DataChannel の `close`、`connectionState` の `failed`、または **10 秒間 相手から何も届かない**
- ホストはその車を「リタイア」として全員に `raceEvent` で通知し、コースから取り除く。レースは残りの人数で続ける。その枠は空きに戻る
- 接続は切れていないが車の状態が届かない場合 (タブを裏に回したなど) は、「ホストのタブがバックグラウンドに回ったときの対策」の 5 の規則 (3 秒でゴースト、60 秒でリタイア) に従う
- レース中の再参加は受け付けない (`reject` の `raceInProgress`)。ロビーに戻ってから、新しい招待リンクで参加し直せる

### 時刻合わせ

- スタートを全員同時にするため、`ping` / `pong` で往復時間を測ってホストの時刻との差を推定し (NTP と同じ考え方)、`raceStart` の時刻に合わせて各自カウントダウンする。ホストの時刻は Worker の時刻 (「対策」の節の 3)。直近 10 回のうち往復時間が短いもの 3 回の平均を使う (再送のない `state` チャンネルでも往復時間はばらつくため)
- 参加者のシミュレーション時刻は、推定したホスト時刻に **毎フレーム ずれの 5% ずつ** 寄せる。ずれが **250 ms 以上** になったら一度に合わせ直す (タブが裏に回っていた後など)

### ホストによる判定と不正対策

数値はすべて `src/shared/net/netRaceRules.ts` にまとめる。

| 項目 | 規則 |
| --- | --- |
| 周回 | チェックポイントを順番どおりに通過したときだけ数える (ショートカット防止) |
| 判定に使う時刻 | 状態の到着時刻 − 往復遅延 / 2 を基準にし、申告された状態の時刻はその ±100ms に丸める。ホストの今の時刻より 100ms 以上先の時刻は今の時刻に丸める |
| 移動の上限 | 前回の状態からの移動が「速さの上限 × 経過時間 + 余裕」を超えたら捨てる。余裕は上限 30 px で、使った分は 30 px/秒ずつ戻る (1 通ごとに足すと積み重ねて速く走れるため) |
| 速さの上限 | 基本の最高速 vBase × (1 + 上乗せの上限 bonusCap) × 1.3。接触を受けてから 1 秒はその 2 倍 (受けた側だけ) |
| 壁 | 壁の中の位置、前回の位置から壁を横切る移動 (8 px 間隔で調べる) は捨てる |
| `collision` の中継 | 2 台の最後の位置の距離が、当たり判定の外接円の直径 × 2 (約 84 px) 以内のときだけ中継する。衝撃が 1,100 px/秒を超えるものは中継しない。10,000 px/秒を超えるものは不正なメッセージとして送り主を切断する |
| コース復帰 (置き直し) | 前回の置き直しから 4.8 秒 (暗転 + 操作不能 + 復帰後のゴースト) 以上あけたときだけ認める。置き直し先はホストの判定した置き直し先から 300 px 以内で、最後に正常に走っていた地点より前に出ない (許容 20 px) |
| 申告のゴースト | 参加者が申告するゴースト (コース復帰後・ピット出口後) は、ピットレーン内とゴール後を除き連続 8 秒まで。超えた分は認めない |
| フライング | 「フライング」の節 |
| メッセージの形 | サイズ上限 (`state` 1,000 バイト、`event` 16KB) と形式のチェックを行い、不正なものを送った参加者は切断する |
| 受信頻度 | `state` は 1 人あたり 60 回/秒、`event` は 20 回/秒 (1 秒の窓で数える)。超えた分は捨て、10 秒続いたら切断する |
| `join` しない相手 | DataChannel が開いてから 5 秒以内に `join` が来なければ切断する |

## 実装ステップ (M4)

| ステップ | 内容 | 状態 |
| --- | --- | --- |
| 1. コードと接続 | 招待・返答コードのエンコード/デコード、`RTCPeerConnection` と DataChannel 2 本の確立、non-trickle の候補収集 | 実装済み |

| 3. ホストの Worker | `hostWorker.ts`、`HostRelay`、`LocalTransport` (ホスト本人) | 実装済み |
| 4. ロビー画面 | `HostLobbyScene` / `GuestLobbyScene`。招待リンク、自動コピー、貼り付け、自動振り分け、注意書き、参加者一覧、準備完了 | 実装済み (2026-09-26 に手順を短縮) |
| 5. 車の状態の送受信 | 他車の補間表示、状態が届かない車のゴースト化 | 実装済み |
| 6. ホストによるレース進行 | カウントダウン、周回判定、順位、結果を Worker で | 実装済み |
