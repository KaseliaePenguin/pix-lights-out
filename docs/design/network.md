## 前提と要件

- ゲーム: トップダウン視点の F1 風レースゲーム (Canvas 2D、固定 60fps 更新)
- 接続形態: P2P のホスト・クライアント方式。マッチング・シグナリング (接続情報の仲介)・中継のサーバーは用意しない
- 接続方法: ホストが参加者ごとに「招待コード」を発行し、チャット (Discord、LINE など) で手渡しする。参加者は「返答コード」を送り返す
- 人数: 最大 8 人
- 想定環境: 同一 LAN、およびインターネット越し (ポート開放は不要)
- 遊ぶ人に必要なもの: モダンブラウザだけ (Node.js やコマンド操作は不要)
- ゲーム本体 (Vite でビルドした静的ファイル) は、どこか 1 か所から https で配信する必要がある (配信先は未決定。「未決定事項」参照)。これは静的ファイルの置き場所で、通信には関わらない

## ブラウザで対戦するときの制約

1. **ブラウザは接続を待ち受けられない**: Web ページの JavaScript は TCP/UDP ポートを開いて待ち受けられない。WebRTC は双方が同時に相手へ接続を試みる仕組み (ICE) なので、待ち受けなしで P2P 接続できる。ただし接続前に、互いの接続情報 (SDP: 暗号鍵の指紋、ICE の認証情報、接続先候補の IP とポート) を何らかの方法で交換する必要がある。方式 D ではこれを人間のコピペで行う
2. **NAT の種類によってはつながらない**: STUN で調べた「外から見た自分の IP・ポート」を教え合い、双方から同時に送って NAT に穴を開ける (ホールパンチ)。対称 NAT (宛先ごとにポートが変わる NAT) 同士などでは穴が開かず、TURN (中継) なしでは接続できない
3. **ブラウザはローカル IP を隠す**: Chrome・Firefox・Safari は、ローカル IP を含む接続先候補 (host 候補) を `xxxxxxxx.local` 形式のランダムな名前 (mDNS) に置き換える。同一 LAN なら名前解決できるので接続できるが、Tailscale などの仮想 LAN 越しには名前解決が届かず、仮想 LAN の IP は使えない
4. **タブがバックグラウンドに回ると止まる**: `requestAnimationFrame` が止まり、メインスレッドのタイマーは最大 1 秒間隔 (Chrome では 5 分後から 1 分間隔) に間引かれる。ホストのタブでレースを進めると、ホストが別タブに切り替えただけでレース全体が止まる (「ホストのタブがバックグラウンドに回ったときの対策」の節)

## 方式の比較

| 方式 | 構成 | 自前サーバー | インターネット越し | 通信品質 | 手間 |
| --- | --- | --- | --- | --- | --- |
| A. Node ホストサーバー + WebSocket | ホストが `npm run host` で Node プロセスを起動し TCP ポートで待ち受け、全員ブラウザから `ws://<ホストIP>:<ポート>` に接続 | 必要 (ホストの PC で Node を動かす) | ホストのポート開放が必要。キャリアグレード NAT では不可 | ○ LAN は問題なし。ロスが多いとカクつく (TCP) | 遊ぶ人: 大 (Node 導入・コマンド・ファイアウォール・ポート開放) / 開発: 小 |
| B. WebRTC DataChannel (A をシグナリングに使用) | A の WebSocket で接続情報だけ交換し、ゲームデータは WebRTC で送る | 必要 (A と同じ) | A と同じ条件 + STUN 依存 | ◎ | 遊ぶ人: 大 / 開発: 大 |
| C. デスクトップアプリ化 (Electron / Tauri) | アプリ本体がポートを開いて待ち受ける | 不要 (アプリが待ち受け) | ポート開放が必要 | ◎ UDP を直接使える | 遊ぶ人: 中 (インストール) / 開発: 大 (配布・パッケージング) |
| **D. ブラウザ同士の WebRTC、コードのコピペで接続 (採用)** | 招待コード・返答コード (SDP を圧縮したもの) をチャットで手渡しし、ブラウザ同士が直接つながる | **不要** (公開 STUN のみ利用) | ポート開放不要。多くの家庭回線でつながるが、対称 NAT 等の組み合わせでは不可 | ◎ 状態は順序保証なし・再送なしで送れる | 遊ぶ人: 中 (1 人 1 往復のコピペ) / 開発: 中 |

### D を採用する理由

- **遊ぶ人がブラウザだけで完結する**: ページを開いてコードをコピペするだけ。Node の導入、コマンドの実行、ファイアウォールの許可ダイアログ、ルーターのポート開放がいらない
- **自前のサーバーを運用しない**: 常時動くサーバーの費用・保守・障害対応がない。使うのは公開 STUN (応答するだけの無料サービス) とゲーム本体の静的ファイル置き場だけ
- **インターネット越しでもポート開放がいらない**: A では必須だったポート開放が、キャリアグレード NAT のためにそもそもできない回線があった。D はホールパンチでつなぐので、多くの家庭回線 (IPv6 が使える回線を含む) で設定なしにつながる
- **通信品質がよい**: 車の状態を「順序保証なし・再送なし」で送れるので、TCP のようにロスした 1 パケットの再送待ちで後続が詰まることがない
- **外から勝手に接続されない**: 待ち受けるポートがなく、招待コードは 1 人 1 回限りなので、コードを渡した相手以外は接続を試みることもできない

受け入れる弱点と対策:

| 弱点 | 対策 |
| --- | --- |
| コピペの手間 (8 人で 7 往復) | コードを短くする、コピー ボタン、どこでも Ctrl+V で貼り付け、返答コードの自動振り分け、並行して発行 (「接続の手順」の節)。一度つながればロビーに戻っても接続を維持し、何レースでも続けて遊べる |
| 回線の組み合わせによってはつながらない (TURN なし) | 原因を見分けて案内し、「別の人がホストになる」などの回避策を示す |
| ホストのタブがバックグラウンドで止まる | ホストのレース進行を Web Worker で動かす。ホストに「タブを前面に」の注意を出す |
| 公開 STUN (第三者) に依存し、STUN サーバーにも IP が伝わる | STUN サーバーは 2 つ設定し、設定値は 1 か所にまとめて差し替え可能にする。同一 LAN なら STUN なしでもつながる |

### A を採用しない理由

- ホストに Node.js の導入と `npm run host` の実行を求めることになり、「ブラウザで遊ぶゲーム」として参加のハードルが高い
- インターネット越しではホストのポート開放が必須で、ルーター設定の知識が要るうえ、キャリアグレード NAT (一部の光回線・モバイル回線・マンション回線) ではそもそもできない。仮想 LAN ツールの導入を案内するしかなかった
- ポートを公開すると誰でも接続を試みられるため、パスワードや攻撃への備えが必要になる
- TCP のみで、ロス時にカクつく
- A の利点だった「ホストのタブに依存しない」は、D でもホストのレース進行を Web Worker に置くことで大部分をカバーできる (完全ではない。対策の節を参照)

B は A のサーバーが結局必要なので採用しない。C は配布とインストールの負担が大きく、ポート開放の問題も残るので採用しない。

## 全体構成

```
ホストのブラウザ (1 タブ)
┌──────────────────────────────────────────────────────┐
│ Web Worker (src/host/)                                 │
│  ・レース進行・判定 (カウントダウン、周回、順位、ゴール)  │
│  ・スナップショット生成 (30 回/秒)、ping (1 回/秒)       │
│             ▲ postMessage (ArrayBuffer は転送)          │
│             ▼                                          │
│ メインスレッド                                          │
│  ・中継 (HostRelay): DataChannel ⇔ Worker (イベント駆動) │
│  ・RTCPeerConnection × 最大 7 (各 2 本の DataChannel)    │
│  ・ホスト本人のゲーム (自車の物理・描画)                 │
│    → Worker とは LocalTransport でつながる               │
└─────┬───────────────┬──────────────────────┬─────────┘
      │ DataChannel ×2 │                      │
      ▼               ▼                      ▼
  参加者 1 のブラウザ   参加者 2 ...            参加者 7

接続前だけ: 各ブラウザ ─(STUN 問い合わせ)→ 公開 STUN サーバー
接続情報:   ホスト ─招待コード→ (チャット) → 参加者 ─返答コード→ (チャット) → ホスト
```

- 参加者同士は直接つながらない (星形)。接触の通知などはホストが中継する
- ホスト本人も「1 人の参加者」として、ネットワーク越しの参加者と同じメッセージ形式で Worker と話す (処理を 1 通りにできる。方式 A で `localhost` に接続していたのと同じ考え方)
- `RTCPeerConnection` は Worker では使えないので、メインスレッドに置く。メインスレッドは受信したものを Worker に渡すだけで、タイマーを持たない (バックグラウンドでの間引きの影響を受けない)
- ディレクトリ案:

| 場所 | 置くもの | DOM 依存 |
| --- | --- | --- |
| `src/shared/` | 車の物理・コース判定 (既存)、メッセージ定義、状態のバイナリ形式 (`src/shared/net/`)、招待・返答コードのエンコード/デコード、レース進行の判定ロジック (周回・順位・ゴール・不正チェック) | なし (Worker からも使う) |
| `src/host/` | ホストのブラウザでだけ動く部分: Worker の入口 (`hostWorker.ts`)、ホストのレース進行 (`RaceHost`)、中継 (`HostRelay`)、招待コードの発行と返答コードの受け付け | Worker 側はなし、中継はメインスレッド |
| `src/net/` | 両方の役で使うブラウザ側の通信: `Transport` インターフェース、WebRTC 実装、`LocalTransport`、STUN 等の設定値 | あり |
| `src/scenes/` | `LobbyScene` (ロビー画面) | あり |

- Worker は Vite の `new Worker(new URL('./hostWorker.ts', import.meta.url), { type: 'module' })` 形式で読み込む (ビルドで別ファイルになる)
- 方式 A で予定していた `server/` ディレクトリと `npm run host` は作らない

## 接続の手順 (UI の流れ)

### 全体の流れ

```
ホスト                                   参加者 (1 人ぶん)
─────────────────────────────           ─────────────────────────────
メニュー → マルチプレイ → ロビーを作る
名前・チームを決める
[招待コードを発行] (1〜5 秒 準備中)
コードが出る → [コピー]
     └──── チャットで送る ─────────→  メニュー → マルチプレイ → ロビーに参加
                                        名前・チームを決める
                                        招待コードを貼り付け (Ctrl+V / [貼り付け])
                                        (1〜5 秒 準備中)
                                        返答コードが出る → [コピー]
     ┌──── チャットで送る ←─────────┘   「ホストの操作を待っています (残り 120 秒)」
返答コードを貼り付け (Ctrl+V / [貼り付け])
「接続中…」(最大 15 秒)
参加者一覧に追加される                  ロビー画面 (参加者一覧) に入る
```

8 人なら、これを参加者 7 人ぶん行う (7 往復)。複数人ぶんは並行して進められる。

### ホストの画面 (ロビーを作る)

| 要素 | 内容 |
| --- | --- |
| 参加者一覧 | 8 枠。枠 0 はホスト本人。枠 1〜7 は状態を表示: 空き / 招待中 (コード発行済み、残り時間) / 接続中 / 参加済み (名前・チーム色・準備状態・接続経路 LAN/NET・往復遅延 ms) / 失敗 (理由) |
| [招待コードを発行] | 空いている枠を 1 つ使って招待コードを作る。押すたびに次の枠のコードを作る (7 人ぶん先にまとめて発行してよい) |
| 招待コード欄 | 選択中の枠のコード (読み取り専用)、[コピー] ボタン、「枠 3 用」の表示、有効期限の残り、注意書き (「セキュリティと注意」の節) |
| 返答コードの貼り付け | 画面のどこでも Ctrl+V で貼り付けられる。[貼り付け] ボタンもある。どの枠への返答かはコードの中身で自動判別するので、貼り付け先を選ぶ必要はない |
| [取り消し] | 招待中・失敗の枠を空きに戻す (発行済みのコードは無効になる) |
| ホスト設定 | 周回数、コースなど (パスワードは不要。招待コードが 1 人 1 回限りのため) |
| 注意 | 「レース中はこのタブを閉じたり再読み込みしないでください」(「ホストのタブがバックグラウンドに回ったときの対策」の節) |

### 参加者の画面 (ロビーに参加)

| 要素 | 内容 |
| --- | --- |
| 招待コードの貼り付け | 画面のどこでも Ctrl+V、または [貼り付け] ボタン。貼り付けた瞬間に形式・バージョンを確認する |
| 返答コード欄 | 読み取り専用、[コピー] ボタン、注意書き、「ホストの操作を待っています (残り 120 秒)」 |
| [やり直す] | 最初 (招待コードの貼り付け) に戻る |
| 接続後 | ホストと同じ参加者一覧 (ホストから `lobby` で届く) と準備完了ボタン |

- Canvas にはテキスト入力がないので、コードの表示・貼り付けは `paste` イベント (`clipboardData`) と `navigator.clipboard` を使う。コピーできない環境 (権限の拒否など) のために、コードを選択できる表示 (DOM の読み取り専用テキスト欄を Canvas に重ねる) も用意する。見た目は art-director が決める
- `navigator.clipboard` は安全なコンテキスト (https または `localhost`) でのみ使えるので、ゲーム本体は https で配信する

### 手間を減らす工夫

1. **ICE 候補を集め終えてからコードを出す (non-trickle)**: 通常の WebRTC は接続先候補を後から小出しに送る (trickle) が、コピペでは往復が増えるので、候補の収集 (`iceGatheringState` が `complete`) を待ってから 1 本のコードにまとめる。収集は最大 **5 秒** で打ち切り、それまでに集まった候補で出す (STUN が応答しない場合に長く待たせないため)
2. **コードを短くする**: SDP 全文 (500〜1,500 文字) をそのまま渡さず、接続に必要な値だけを取り出してバイナリに詰め、Base64url (URL やチャットで崩れない `A-Z a-z 0-9 - _` のみ) にする。受け取った側は固定のひな形に値を埋めて SDP を組み立て直す (詳細は次節)
3. **コピー ボタンと、どこでも貼り付け**: コードは [コピー] 1 回でクリップボードに入る。貼り付けは入力欄を選ばなくても Ctrl+V で受け付け、コードの種類 (招待 / 返答) も自動判別する
4. **返答コードの自動振り分けと並行発行**: ホストは招待コードを枠ごとに先にまとめて発行し、全員に一斉に送れる。返答コードには枠番号とロビー ID が入っているので、届いた順に同じ場所へ貼り付けるだけでよい
5. **一度つながれば維持する**: レースが終わってロビーに戻っても接続は切らない。同じメンバーなら何レースでも続けて遊べ、コピペはセッションの最初だけで済む。コードの再利用 (次回の起動時に同じコードで入る) はできない (WebRTC の認証情報が接続ごとに使い捨てのため)

### 1 本のコードで複数人を受け付けられないか (検討)

| 案 | 内容 | 評価 |
| --- | --- | --- |
| 1 つの招待を複数人で使う | 1 つの offer (招待) に複数人が answer (返答) する | **不可**。WebRTC の 1 つの接続 (`RTCPeerConnection`) は 1 対 1 で、offer の ICE 認証情報・暗号鍵の指紋も 1 つの接続に結びつく |
| まとめ招待コード | 7 人ぶんの offer を 1 本に詰め、参加者は自分の枠番号を選んで返答する | 可能だが**採用しない**。長さは約 7 倍 (約 800 文字) になり、枠番号の重複 (2 人が同じ枠を選ぶ) の扱いが要る。返答コードは結局 7 本必要なので、減るのはホストの「コピー」操作だけ。個別コードをまとめて発行してチャットに並べて貼るのと手間がほぼ同じ |
| 参加者同士の中継 | つながった参加者経由で次の人の接続情報を渡す | 不可。まだ誰ともつながっていない人には、コピペ以外に情報を渡す経路がない |

結論: **1 人 1 往復の個別コード + 並行発行 + 自動振り分け** とする。

### コードの形式と長さ

```
PLO1I.<Base64url>   招待コード (Invite)
PLO1R.<Base64url>   返答コード (Reply)
```

- 先頭の `PLO` はゲーム名、`1` はコード形式のバージョン、`I` / `R` は種類。チャットで改行や空白が混ざっても、貼り付け時に空白・改行を取り除いてから読む
- 中身 (バイナリ、多バイトはビッグエンディアン):

| 項目 | バイト数 | 招待 | 返答 | 備考 |
| --- | --- | --- | --- | --- |
| プロトコルのバージョン | 2 | ○ | ○ | メッセージ形式・物理の互換性の番号。違えば貼り付けた時点で拒否 |
| ロビー ID | 4 | ○ | ○ | ホストがロビー作成時に乱数で作る。別のロビーへの返答を見分ける |
| 枠番号 | 1 | ○ | ○ | 1〜7 |
| フラグ | 1 | ○ | ○ | STUN の応答なし、対称 NAT の疑い、SDP 全文形式 (下記) |
| ICE ufrag | 1 + 4〜32 | ○ | ○ | 長さ + 文字列 (Chrome は 4 文字) |
| ICE pwd | 1 + 22〜32 | ○ | ○ | 長さ + 文字列 |
| DTLS 指紋 (SHA-256) | 32 | ○ | ○ | 暗号化の相手確認に使う。これが一致しない相手とはつながらない |
| 接続先候補 | 1 + 候補ごと 7〜19 | ○ | ○ | 候補数 + [種類 1 (host/srflx、IPv4/IPv6/mDNS) + アドレス (IPv4 は 4、IPv6 と mDNS の UUID は 16) + ポート 2]。UDP のみ、最大 6 個 |
| チェックサム | 2 | ○ | ○ | コピー漏れ (途中で切れた) を検出する |

- 固定の値は入れない (ひな形側に持つ): `m=application ... webrtc-datachannel`、`a=setup` (招待は `actpass`、返答は `active`)、`a=mid:0`、`a=sctp-port:5000`、`a=max-message-size`、候補の優先度と foundation (種類から決める)
- 名前・チームなどはコードに入れず、接続後に `join` で送る (コードを短く保つ)
- **長さの目安**: 候補 2〜4 個 (mDNS の host 候補 + IPv4 の srflx 候補 + IPv6 の候補) で 約 100〜170 バイト → **約 140〜230 文字**。上限の目安は 300 文字 (チャットの 1 メッセージに収まり、目で見ても「長い 1 行」程度)
- 汎用の圧縮 (deflate) は、この大きさでは中身の大半が乱数 (認証情報・指紋) のためほとんど縮まないので使わない。ただし、SDP が想定外の形 (ブラウザの仕様変更など) で値を取り出せなかった場合だけ、フラグを立てて **SDP 全文を deflate 圧縮 + Base64url** で入れる (約 500〜1,000 文字。長いがつながる)
- エンコード・デコードは DOM に依存しない純粋な関数として `src/shared/net/` に置き、単体で確認できるようにする

## Transport の設計

ゲーム側 (シーン、ホストのレース進行) は `Transport` インターフェース越しに通信し、WebRTC を直接触らない。

### インターフェース (案)

参加者側 `ClientTransport`:

| メンバー | 内容 |
| --- | --- |
| `sendState(data: ArrayBuffer)` | 状態を送る (届かなくてよい) |
| `sendEvent(msg)` | イベントを送る (必ず順番どおり届く) |
| `onState` / `onEvent` | 受信時に呼ばれる |
| `onClose(reason)` | 切断時に呼ばれる (`hostClosed` / `connectionFailed` / `timeout`) |
| `close()` | 切断する |
| `stats` | 往復遅延 (ms)、接続経路 (`lan` / `internet`) |

ホスト側 `HostTransport` (Worker 内で使う):

| メンバー | 内容 |
| --- | --- |
| `sendState(peerId, data)` / `broadcastState(data)` | 状態を 1 人 / 全員に送る |
| `sendEvent(peerId, msg)` / `broadcastEvent(msg)` | イベントを 1 人 / 全員に送る |
| `onPeerJoin(peerId)` / `onPeerLeave(peerId, reason)` | 参加・離脱 |
| `onState(peerId, data)` / `onEvent(peerId, msg)` | 受信 |
| `kick(peerId, reason)` | 切断する (不正なメッセージなど) |

実装:

| 実装 | 使う場所 | 中身 |
| --- | --- | --- |
| `WebRtcClientTransport` | 参加者 | `RTCPeerConnection` 1 つ + DataChannel 2 本 |
| `LocalTransport` | ホスト本人のゲーム | Worker と `MessagePort` でつなぐ。遅延ほぼ 0 |
| `WorkerHostTransport` | ホストの Worker | メインスレッドの `HostRelay` と `postMessage` でやりとりし、`HostRelay` が各参加者の DataChannel に振り分ける |
| `LoopbackTransport` | 開発・確認用 | 1 つのタブの中で疑似的に複数人をつなぐ。遅延・ロスを擬似的に入れられるようにする |

### DataChannel は 2 本

| チャンネル | 設定 | 流すもの | 形式 |
| --- | --- | --- | --- |
| `state` | `ordered: false`, `maxRetransmits: 0` (順序保証なし・再送なし) | `carState`、`snapshot`、`ping` / `pong` | バイナリ |
| `event` | `ordered: true`、再送あり (既定) | それ以外すべて (`join`、`lobby`、`raceStart`、`raceEvent`、`collision`、`result`、`hostClosed` など) | JSON 文字列 |

- 2 本とも `negotiated: true` と固定の `id` (`state` = 0、`event` = 1) で両側が作る。相手側の `ondatachannel` を待つ必要がなく、コードにチャンネル情報を入れなくてよい
- `binaryType = 'arraybuffer'`
- `state` の 1 メッセージは **1,000 バイト以下** にする。大きいと内部で分割され、1 片でも失うと全体が失われる (8 台ぶんのスナップショットは 約 250 バイトで収まる)
- 状態は古いものに価値がないので、各メッセージに連番を付け、受信側は最新より古い連番を捨てる (順序保証なしのため)
- `ping` / `pong` を `state` に流すのは、再送による遅れが遅延の測定値に混ざらないようにするため。失われた `ping` は数えない
- 送信が詰まったとき: `state` は `bufferedAmount` が 16KB を超えていたらその回の送信を捨てる。`event` は捨てない
- `collision` は再送ありの `event` で送る (取りこぼすと接触が片側だけになるため)。受信時に、接触時刻から 250ms 以上経っていたら適用しない (遅れて届いた衝撃で急に弾かれるのを防ぐ)
- 受信サイズの上限: `state` 1,000 バイト、`event` 16KB。超えたら切断 (「ホストによる判定と不正対策」)

## ホストのタブがバックグラウンドに回ったときの対策

### 何が起きるか

| 場所 | バックグラウンドでの挙動 |
| --- | --- |
| `requestAnimationFrame` | 止まる |
| メインスレッドの `setTimeout` / `setInterval` | 最大 1 秒に 1 回に間引かれる。Chrome は隠れて 5 分後から 1 分に 1 回 |
| DataChannel・`postMessage` の受信処理 | 届いたときに実行される (タイマーではないので間引かれない) |
| 専用 Web Worker のタイマー | 間引かれない (主要ブラウザの現状の挙動。仕様で保証されたものではないので、実機で確認する) |
| タブの凍結 (省メモリ機能など) | WebRTC 接続があるタブは対象外とされるが、ブラウザとバージョンに依存するので頼らない |

### 方針

1. **ホストのレース進行・判定は Web Worker で動かす**: カウントダウン、周回・チェックポイント判定、順位、ゴール、不正チェック、スナップショット生成 (30 回/秒)、`ping` (1 回/秒) は Worker の中のタイマーで進める。ホストのタブが隠れてもレースは止まらない
2. **メインスレッドはイベント駆動の中継だけ**: DataChannel で受けたものを Worker に渡し、Worker から来たものを DataChannel に送る。タイマーを使わないので間引きの影響を受けない
3. **ホストの時刻**: Worker の `performance.timeOrigin + performance.now()` をホスト時刻とする (メインスレッドとは基準が違うので混ぜない)
4. **ホスト本人の車**: ホスト本人の車の物理と描画はメインスレッドで動くので、タブが隠れると止まる。これは参加者がタブを隠した場合と同じ扱いにする (次項)
5. **車の状態が届かない車の扱い (ホスト本人も参加者も同じ規則)**:

| 状態が届かない時間 | 扱い |
| --- | --- |
| 3 秒 | その場で止まったまま **ゴースト (すり抜け)** にする (game-design.md 7.10 節のゴーストと同じ: 当たり判定なし)。他の車がぶつからないようにするため。状態が再び届けば通常に戻る (戻るときは 7.10 節の「重なっている間は延長」に従う) |
| 60 秒 | リタイア扱い (`raceEvent`)。接続は切らず、ロビーに戻れば次のレースに出られる |

6. **ロビーでは切断しない**: 生存確認は `ping` / `pong` で行う。`pong` はメインスレッドが受信処理の中ですぐ返すので、タブが隠れていても返せる。ロビーで何分タブを離れても切れない
7. **ホストへの注意表示**:
   - ロビー (ホストの画面、常時): 「ホストへ: レース中はこのタブを閉じたり再読み込みしないでください。別のタブに切り替えてもレースは続きますが、あなたの車は止まります」
   - レース開始時 (ホストだけ、メッセージ帯で 3 秒): 「ホストはこのタブを前面にしたままにしてください」
   - タブが前面に戻ったとき、隠れていた時間が 3 秒以上ならメッセージ帯で「タブが裏に回っていたため、車が止まっていました」
   - ホストがタブを閉じる・再読み込みしようとしたら、参加者がいる間は `beforeunload` で確認ダイアログを出す
   - パソコンのスリープでは全員の接続が切れる (防げない)。ロビーの注意書きには含めず、操作説明 (HelpScene) に書く

## 接続できなかったときの扱い

### 待ち時間の上限

| 段階 | 上限 | 超えたら |
| --- | --- | --- |
| 接続先候補の収集 (招待・返答コードを作るとき) | 5 秒 | 集まった候補でコードを出す。srflx 候補が 1 つもなければ「STUN の応答なし」フラグを立てる |
| 招待コードの有効期限 (ホスト) | 10 分 | 枠を「失敗 (期限切れ)」にする。後から返答コードが来たら期限切れと表示 (NAT の対応付けが時間で消え、つながらなくなるため) |
| 返答コードを出してからホストが貼り付けるまで (参加者) | 120 秒 | 参加者に「時間切れ」を表示して最初に戻す。ホストには新しい招待コードの発行を案内する |
| ホストが返答コードを貼ってから接続完了まで (ICE 確認 → DataChannel 2 本が開く → `join` / `welcome`) | 15 秒 | 「失敗」として原因を判定する |

### 原因の見分け

| 状況 | 見分け方 | 案内文 (ホスト / 参加者の画面) |
| --- | --- | --- |
| コードが壊れている | 先頭が `PLO` でない、Base64url として読めない、チェックサムが合わない | 「コードが正しくありません。途中で切れていないか確かめて、もう一度コピーしてください」 |
| 種類が違う | 参加者が返答コード (`R`) を、ホストが招待コード (`I`) を貼った | 「これは返答コードです。ホストから届いた招待コードを貼り付けてください」/「これは招待コードです。参加者から届いた返答コードを貼り付けてください」 |
| バージョン違い | プロトコルのバージョンが違う | 「ゲームのバージョンが違います。全員ページを再読み込みして最新にしてください」 |
| 別のロビー・使用済み・期限切れ | ロビー ID が違う / 枠がすでに参加済み / 期限切れ | 「このロビーへの返答コードではありません」/「この枠はすでに使われています」/「期限切れです。新しい招待コードを発行して送ってください」 |
| STUN に届かない | 自分の候補に srflx がない (コードのフラグで相手の状態も分かる) | コード発行時に警告: 「インターネット越しの接続情報を取得できませんでした。同じ LAN の相手とだけ接続できます (UDP 通信が制限されたネットワークの可能性があります)」 |
| 対称 NAT の疑い | 2 つの STUN サーバーから得た srflx 候補が、同じ元ポートに対して違うポートになっている | コード発行時に注意: 「あなたの回線は接続しにくい種類かもしれません。つながらない場合は、別の人にホストを代わってもらってください」 |
| 接続の確立に失敗 (ICE の失敗) | `iceConnectionState` / `connectionState` が `failed`、または 15 秒以内に `connected` にならない | 下記の「つながらなかったとき」の案内 |
| 同じ LAN にいるのに失敗 | 双方の srflx の IP が同じ (同じルーターの内側) なのに ICE が失敗 | 「同じネットワークにいるようですが接続できませんでした。ゲスト用 Wi-Fi など、端末同士の通信を禁止しているネットワークでは遊べません。別のネットワークに切り替えてください」 |
| つながった後の応答なし | DataChannel が開いたのに 5 秒以内に `welcome` / `join` が来ない | 「接続後の応答がありません。ページを再読み込みしてやり直してください」 |

**つながらなかったとき** の案内文 (ホスト・参加者の両方に表示):

> 接続できませんでした。
> お互いの回線の組み合わせ (対称 NAT、キャリアグレード NAT、厳しいファイアウォールなど) によっては、この方式ではつながらないことがあります。次を試してください。
> 1. もう一度やり直す (新しい招待コードで)
> 2. 別の人にホストを代わってもらう
> 3. どちらかがスマートフォンのテザリングなど、別の回線を使う
> 4. 同じ LAN (同じ Wi-Fi) で遊ぶ

- 失敗した枠には [詳細をコピー] ボタンを付け、原因の調査用に状態の記録 (候補の種類と数、ICE の状態の移り変わり、フラグ、経過時間) をコピーできるようにする。**IP アドレスは記録に含めない**
- 仮想 LAN (Tailscale など) はこの方式では回避策にならない (ブラウザがローカル IP を隠すため) ので、案内に含めない

### 同一 LAN の場合

- 同一 LAN では mDNS の host 候補同士で直接つながるので、**STUN に届かなくても (インターネットにつながっていなくても) 接続できる**。STUN の応答がなくてもエラーにはせず、上記の警告だけを出してコードを発行する
- 参加者一覧の接続経路は、実際に使われている候補の組 (`getStats` の選ばれた候補ペア) が host 同士なら `LAN`、それ以外なら `NET` と表示する

### 使う STUN サーバー

- `stun:stun.l.google.com:19302` と `stun:stun.cloudflare.com:3478` の 2 つ (対称 NAT の判定に 2 つ必要)
- 設定値は `src/net/` の 1 か所にまとめ、差し替えられるようにする
- IPv6 の srflx 候補も使う。IPv4 がキャリアグレード NAT でも IPv6 が使える回線 (国内の IPoE 回線に多い) なら、IPv6 で直接つながることが多い

## セキュリティと注意

### コードに IP アドレスが含まれる

- 招待・返答コードには、**その人の回線のグローバル IP アドレス** (srflx 候補) が含まれる。ブラウザがローカル IP を隠す設定になっていない場合は LAN の IP も含まれる
- コードの [コピー] ボタンの近くに、常に次の注意書きを出す:

> このコードには、あなたのインターネット回線の IP アドレスが含まれます。一緒に遊ぶ信頼できる相手にだけ、個別に (DM などで) 渡してください。SNS や公開の場所には貼らないでください。

- コードは 1 人 1 回限りで、使った後や期限切れ後は誰も接続に使えない。ただし IP アドレスが見えることには変わりないので、注意書きは常に出す
- STUN サーバー (Google、Cloudflare) にも、問い合わせのときにグローバル IP が伝わる。操作説明に記載する

### 通信の保護

- DataChannel は DTLS で必ず暗号化される。コードに入っている暗号鍵の指紋と一致する相手としかつながらないので、コードを渡した相手以外が割り込むことはできない (コードを受け渡すチャットが信頼できる前提)
- 待ち受けるポートがないので、外部から接続を試みられることはない。方式 A で予定していた参加パスワードは不要

### ホストの権限

- レース進行と判定 (スタート時刻、フライング、周回・チェックポイント、順位、ゴール、ペナルティ、リタイア) はすべてホストが行い、参加者はホストの判定に従う
- ホストのブラウザでは判定を書き換えることも技術的には可能。「知り合い同士で遊ぶ」前提として、ホスト自身の不正は防がない
- ホストは参加者からの受信を検証する (「ホストによる判定と不正対策」)。参加者もホストからの受信について、サイズ上限と形式のチェックだけは行い、壊れたものは捨てる

## 同期方式

レースゲームでは車同士が絡む時間が短く、操作の即応性が最重要なので、次の分担にする。

| 対象 | 担当 | 理由 |
| --- | --- | --- |
| 自分の車の挙動 | 各クライアント (自分で計算) | 入力遅延ゼロで操作できる。ホスト側で全車を計算すると、ホストから遠い人ほど操作が遅れる |
| 他の車の表示 | 受け取った位置を補間して描画 | 約 100ms 過去の状態を 2 点間で補間し、なめらかに見せる |
| レース進行 (カウントダウン、周回、順位、ゴール、失格) | ホスト (Worker) | 全員で結果を一致させ、不正を防ぐ |
| 車同士の接触 | 各クライアントが自分の車の反応を計算し、ホストが仲介して相手にも伝える | 詳細は「車同士の接触」の節 |

「クライアント」はホスト本人を含む全プレイヤーのゲーム画面を指す (ホスト本人は `LocalTransport` で Worker とつながる)。

### 送信内容と頻度

- クライアント → ホスト: 自分の車の状態 (位置、向き、速度、通過したチェックポイント) を **毎秒 30 回** (`state` チャンネル)
- ホスト → 全員: 全車の状態をまとめたもの (スナップショット) を **毎秒 30 回** (`state` チャンネル、Worker のタイマーで送る)
- 状態データはバイナリ (`ArrayBuffer` + `DataView`、1 台あたり 20〜30 バイト程度 + 連番) で送る。ロビーやイベントなど頻度の低いメッセージは JSON (`event` チャンネル)
- 目安の通信量: 8 台 × 30 バイト × 30 回/秒 ≒ 7KB/秒 (ホストの送信はこれ × 7 人)。家庭回線で問題にならない

### メッセージ一覧 (案)

| 方向 | 種類 | チャンネル | 内容 |
| --- | --- | --- | --- |
| C→H | `join` | event | プレイヤー名、チーム、プロトコルのバージョン |
| H→C | `welcome` / `reject` | event | 割り当てたプレイヤー ID、参加者一覧 / 拒否理由 (満員、バージョン違い、名前・チームの重複など) |
| H→全 | `lobby` | event | 参加者一覧、準備状態、コース、ホスト設定 |
| C→H | `ready` | event | 準備完了 |
| H→全 | `raceStart` | event | スタート時刻 (ホスト時刻)、グリッド位置 |
| C→H | `carState` | state | 自分の車の状態 (バイナリ、連番付き) |
| H→全 | `snapshot` | state | 全車の状態 (バイナリ、連番付き) |
| H→全 | `raceEvent` | event | 周回通過、ゴール、失格、リタイア、ゴースト化、切断 |
| H→全 | `result` | event | 最終順位とタイム |
| C→H→C | `collision` | event | 接触相手の ID、衝撃の向きと大きさ、時刻 (ホストが相手に中継) |
| H→全 | `hostClosed` | event | ホストが終了することの通知 |
| 双方向 | `ping` / `pong` | state | 遅延測定と時刻合わせ、生存確認 (ホストの Worker が 1 回/秒) |

### 車同士の接触

各車は持ち主のクライアントが計算しているため、接触は次の方法で処理する。

1. **近くの車は予測位置で扱う**: 他車は通常 約 100ms 過去の位置を補間して表示するが、それでは当たり判定がずれる。自分の車から一定距離 (例: 車 3 台分) 以内の他車は、最新の位置と速度から「今の位置」を予測して表示・判定に使う
2. **自分の車だけ動かす**: 重なりを検出したら、自分の車を押し戻し、相対速度と重さ (全車同じ) から計算した衝撃を自分の速度に加える
3. **相手にも伝える**: 接触したクライアントはホストに `collision` (相手 ID、衝撃の向きと大きさ、時刻) を送り、ホストが相手に中継する。相手がまだ接触を検出していなければ、受け取った衝撃を自分の車に適用する (接触時刻から 250ms 以上経っていれば適用しない)
4. **二重適用を防ぐ**: 同じ 2 台の組み合わせで短時間 (例: 200ms) 内に 2 回目の衝撃は適用しない

- 遅延が大きい相手ほど、接触の見た目にずれが出る (相手との遅延が 100ms を超えると目立つ)。参加者同士の通信はホスト経由なので、実際の遅延は「自分 → ホスト → 相手」の合計になる。LAN・国内の通信であれば許容範囲の想定
- ホストの不正チェックは、接触による急な速度変化を誤検出しないよう、直前に `collision` がある場合は判定を緩める
- 衝撃の強さ、押し戻し量、スピンの条件は `docs/design/car-physics.md` の「9. 接触 (衝撃)」で決めている (当てた側の判定は両クライアントで同じ式になるので結果が一致する)

### 切断時の扱い

**ホストが抜けた場合 (レース終了)**

- ホストが終了操作をした場合 (ロビーを閉じる、メニューに戻る): 全員に `hostClosed` を送ってから接続を閉じる
- ホストがタブを閉じた・再読み込みした場合: `pagehide` で `hostClosed` を送ってから閉じる (届かないこともあるので、下の検出が最終手段)
- 異常終了・回線切断の場合: クライアントは DataChannel の `close`、`connectionState` の `failed`、または **3 秒間 `snapshot` が届かない** ことで検出する (`disconnected` は一時的に回復することがあるので、それだけでは切断としない)
- どの場合もクライアントはレースを止めて「ホストとの接続が切れました。レースを終了します」と表示し、OK でタイトル画面に戻る
- 結果は記録しない (レースは無効)
- 各参加者はホストとしかつながっていないので、ホストの代わりを立てて続けることはしない

**クライアントが抜けた場合 (レース続行)**

- 検出: DataChannel の `close`、`connectionState` の `failed`、または **10 秒間 `pong` が返らない**
- ホストはその車を「リタイア」として全員に `raceEvent` で通知し、コースから取り除く。レースは残りの人数で続ける。その枠は空きに戻る
- 接続は切れていないが車の状態が届かない場合 (タブを裏に回したなど) は、「ホストのタブがバックグラウンドに回ったときの対策」の 5 の規則 (3 秒でゴースト、60 秒でリタイア) に従う
- レース中の再参加は受け付けない。ロビーに戻ってから、新しい招待コードで参加し直せる

### 時刻合わせ

スタートを全員同時にするため、`ping` / `pong` で往復時間を測ってホストの時刻との差を推定し (NTP と同じ考え方)、`raceStart` の時刻に合わせて各自カウントダウンする。ホストの時刻は Worker の時刻 (「対策」の節の 3)。直近 10 回のうち往復時間が短いもの 3 回の平均を使う (再送のない `state` チャンネルでも往復時間はばらつくため)。

### ホストによる判定と不正対策

- 周回はチェックポイントを順番どおりに通過したときだけ数える (ショートカット防止)
- 前回の状態から計算して車の性能上ありえない移動 (速度上限超え、瞬間移動) は無視して警告する
- 受信メッセージはサイズ上限 (`state` 1,000 バイト、`event` 16KB) と形式のチェックを行い、不正なものを送った参加者は切断する
- 受信頻度の上限: `state` は 1 人あたり 60 回/秒、`event` は 20 回/秒。超えた分は捨て、10 秒続いたら切断する

## 実装ステップ (M4)

1. **コードと接続**: 招待・返答コードのエンコード/デコード (`src/shared/net/`、単体で確認)、`RTCPeerConnection` と DataChannel 2 本の確立、non-trickle の候補収集。まず同じ PC の 2 つのタブで、手でコピペしてつながることを確認する
2. **Transport**: `Transport` インターフェース、`WebRtcClientTransport`、`LoopbackTransport` (1 タブで複数人を擬似的に動かす、遅延・ロスの擬似)、`ping` / `pong` と時刻合わせ
3. **ホストの Worker**: `hostWorker.ts`、`HostRelay` (DataChannel ⇔ Worker の中継)、`LocalTransport` (ホスト本人)。ホストのタブを裏に回しても `ping` とスナップショットが止まらないことを確認する
4. **ロビー画面** (`LobbyScene`): ロビーを作る / 参加する、招待コードの発行 (並行発行)、貼り付け (Ctrl+V・ボタン)、返答コードの自動振り分け、コピー ボタン、注意書き、参加者一覧 (接続経路・遅延)、準備完了
5. **車の状態の送受信** と他車の補間表示、状態が届かない車のゴースト化
6. **ホストによるレース進行** (カウントダウン、周回判定、順位、結果) を Worker で動かす
7. **車同士の接触** (予測位置での判定、`collision` の中継)
8. **切断と失敗の処理**: ホスト切断時のエラー表示とレース終了、クライアントのリタイア、接続失敗の原因判定と案内文、[詳細をコピー]、`beforeunload` の確認、不正対策
9. **実回線での確認**: 同一 LAN (Wi-Fi 同士、有線と Wi-Fi)、別々の家庭回線、スマートフォンのテザリング (キャリアグレード NAT の例) で 2 人・8 人の接続を試し、つながらなかった組み合わせを記録する
