# オンライン対戦 接続方式の検討

状態: **方式 A で進める (2026-09-25 決定)**

## 決定事項

| 項目 | 決定 |
| --- | --- |
| 接続方式 | 方式 A (Node ホストサーバー + WebSocket)。通信層は差し替え可能にしておく |
| 最大人数 | 8 人 |
| 車同士の接触 | あり (「車同士の接触」の節の方式で処理) |
| ホストが途中で抜けた場合 | 全クライアントにエラーメッセージを表示してレース終了 (「切断時の扱い」の節) |

## 前提と要件

- ゲーム: トップダウン視点の F1 風レースゲーム (Canvas 2D、固定 60fps 更新)
- 接続形態: P2P のホスト・クライアント方式。専用のマッチングサーバーは用意しない
- 接続方法: クライアントがホストの **IP アドレスを直接入力** して接続する
- 人数: 最大 8 人
- 想定環境: 同一 LAN、およびインターネット越し (ホスト側でポート開放)

## 最大の制約: ブラウザは接続を待ち受けられない

ブラウザ (Web ページ) の JavaScript は、TCP/UDP ポートを開いて他の端末からの接続を受け付けることができない。
そのため「ブラウザのタブがそのままホストになり、クライアントが IP で接続する」構成は実現できない。
ホスト側には **ポートを開けて待ち受けるプロセス** が必要になる。

加えて、ブラウザのタブはバックグラウンドに回ると `requestAnimationFrame` が止まり、タイマーも最大 1 秒間隔に間引かれる。
ホストのゲーム進行をブラウザのタブに置くと、ホストが別ウィンドウを触っただけでレース全体が止まる危険がある。

## 方式の比較

| 方式 | 構成 | IP 直指定 | 通信品質 | 手間 |
| --- | --- | --- | --- | --- |
| **A. Node ホストサーバー + WebSocket** (推奨) | ホストが `npm run host` で Node プロセスを起動し、TCP ポート (例: 7777) で待ち受ける。全員ブラウザから `ws://<ホストIP>:7777` に接続 | ◎ そのまま実現できる | ○ LAN は問題なし。インターネット越しでパケットロスが多いとカクつく (TCP のため) | 小 |
| B. WebRTC DataChannel (A をシグナリングに使用) | A の WebSocket で接続情報だけ交換し、ゲームデータは WebRTC の UDP 的な通信で送る | △ シグナリングは IP 直指定、本通信は NAT 越えの仕組み (STUN) に依存 | ◎ 順序保証なし・再送なしのモードでロスに強い | 大 (NAT 越え失敗時の対処、デバッグが難しい) |
| C. デスクトップアプリ化 (Electron / Tauri) | アプリ本体がポートを開いて待ち受ける (UDP も可) | ◎ | ◎ UDP を直接使える | 大 (配布・パッケージングが必要) |
| D. ブラウザ同士の WebRTC 手動接続 | 接続情報 (SDP) をコピペで交換 | × IP 直指定にならない | ◎ | 中 (操作が煩雑) |

### 推奨: 方式 A から始める

- 要件の「IP 直指定」「ホスト・クライアント」にそのまま合い、最小の構成で動く
- ホストのゲーム進行を Node プロセスに置くので、タブがバックグラウンドでも止まらない
- ゲーム側は `Transport` インターフェース越しに通信するよう作り、後から B (WebRTC) や C (Electron) に差し替えられるようにする
  - C に移る場合も、ホストサーバーのコードは Electron のメインプロセスでそのまま動く
- TCP の弱点 (ロス時の遅延) は、送信頻度を抑えて補間表示することで実用上カバーする (後述)。インターネット越しで問題が出たら B に移る

## 方式 A の構成

```
ホストの PC                                         クライアントの PC
┌───────────────────────────────┐                  ┌───────────────────┐
│ npm run host                  │                  │ ブラウザ           │
│ ┌───────────────────────────┐ │  ws://<IP>:7777  │ (ゲーム画面)       │
│ │ ホストサーバー (Node)       │◄├──────────────────┤                   │
│ │ ・待ち受け (ws ライブラリ)  │ │                  └───────────────────┘
│ │ ・レース進行・判定          │ │
│ └─────────▲─────────────────┘ │
│           │ ws://localhost:7777│
│ ┌─────────┴─────────┐         │
│ │ ブラウザ (ホスト本人) │         │
│ └───────────────────┘         │
└───────────────────────────────┘
```

- ホスト本人も普通のクライアントとして `localhost` に接続する (処理を 1 通りにできる)
- ゲーム画面 (Vite でビルドした静的ファイル) もホストサーバーから配信すれば、クライアントはブラウザで `http://<ホストIP>:7777` を開くだけで遊べる
  - 別々に配信する場合、ゲーム画面を https で開くと `ws://` に接続できない (混在コンテンツの制限) ので注意
- ディレクトリ案: `src/shared/` (ブラウザとサーバー共通の型・メッセージ定義・物理計算)、`server/` (ホストサーバー)

## 同期方式

レースゲームでは車同士が絡む時間が短く、操作の即応性が最重要なので、次の分担にする。

| 対象 | 担当 | 理由 |
| --- | --- | --- |
| 自分の車の挙動 | 各クライアント (自分で計算) | 入力遅延ゼロで操作できる。ホスト側で全車を計算すると、ホストから遠い人ほど操作が遅れる |
| 他の車の表示 | 受け取った位置を補間して描画 | 約 100ms 過去の状態を 2 点間で補間し、なめらかに見せる |
| レース進行 (カウントダウン、周回、順位、ゴール、失格) | ホスト | 全員で結果を一致させ、不正を防ぐ |
| 車同士の接触 | 各クライアントが自分の車の反応を計算し、ホストが仲介して相手にも伝える | 詳細は「車同士の接触」の節 |

### 送信内容と頻度

- クライアント → ホスト: 自分の車の状態 (位置、向き、速度、通過したチェックポイント) を **毎秒 30 回**
- ホスト → 全員: 全車の状態をまとめたもの (スナップショット) を **毎秒 20〜30 回**
- 状態データはバイナリ (`ArrayBuffer` + `DataView`、1 台あたり 20〜30 バイト程度) で送る。ロビーやイベントなど頻度の低いメッセージは JSON
- 目安の通信量: 8 台 × 30 バイト × 30 回/秒 ≒ 7KB/秒 (ホストの送信はこれ × 人数)。家庭回線で問題にならない

### メッセージ一覧 (案)

| 方向 | 種類 | 内容 |
| --- | --- | --- |
| C→H | `join` | プレイヤー名、ゲームのバージョン、(任意) パスワード |
| H→C | `welcome` / `reject` | 割り当てたプレイヤー ID、参加者一覧 / 拒否理由 (満員、バージョン違いなど) |
| H→全 | `lobby` | 参加者一覧、準備状態、コース |
| C→H | `ready` | 準備完了 |
| H→全 | `raceStart` | スタート時刻 (ホスト時刻)、グリッド位置 |
| C→H | `carState` | 自分の車の状態 (バイナリ) |
| H→全 | `snapshot` | 全車の状態 (バイナリ) |
| H→全 | `raceEvent` | 周回通過、ゴール、失格、切断 |
| H→全 | `result` | 最終順位とタイム |
| C→H→C | `collision` | 接触相手の ID、衝撃の向きと大きさ、時刻 (ホストが相手に中継) |
| H→全 | `hostClosed` | ホストが終了することの通知 |
| 双方向 | `ping` / `pong` | 遅延測定と時刻合わせ |

### 車同士の接触

各車は持ち主のクライアントが計算しているため、接触は次の方法で処理する。

1. **近くの車は予測位置で扱う**: 他車は通常 約 100ms 過去の位置を補間して表示するが、それでは当たり判定がずれる。自分の車から一定距離 (例: 車 3 台分) 以内の他車は、最新の位置と速度から「今の位置」を予測して表示・判定に使う
2. **自分の車だけ動かす**: 重なりを検出したら、自分の車を押し戻し、相対速度と重さ (全車同じ) から計算した衝撃を自分の速度に加える
3. **相手にも伝える**: 接触したクライアントはホストに `collision` (相手 ID、衝撃の向きと大きさ、時刻) を送り、ホストが相手に中継する。相手がまだ接触を検出していなければ、受け取った衝撃を自分の車に適用する
4. **二重適用を防ぐ**: 同じ 2 台の組み合わせで短時間 (例: 200ms) 内に 2 回目の衝撃は適用しない

- 遅延が大きい相手ほど、接触の見た目にずれが出る (相手との遅延が 100ms を超えると目立つ)。LAN・国内の通信であれば許容範囲の想定
- ホストの不正チェックは、接触による急な速度変化を誤検出しないよう、直前に `collision` がある場合は判定を緩める
- 衝撃の強さ、押し戻し量、スピンの条件は `docs/design/car-physics.md` の「9. 接触 (衝撃)」で決めている (当てた側の判定は両クライアントで同じ式になるので結果が一致する)

### 切断時の扱い

**ホストが抜けた場合 (レース終了)**

- ホストが終了操作をした場合: ホストサーバーは全員に `hostClosed` を送ってから接続を閉じる
- 異常終了・回線切断の場合: クライアントは WebSocket の切断、または 3 秒間 `snapshot` が届かないことで検出する
- どちらの場合もクライアントはレースを止めて「ホストとの接続が切れました。レースを終了します」と表示し、OK でタイトル画面に戻る
- 結果は記録しない (レースは無効)

**クライアントが抜けた場合 (レース続行)**

- ホストはその車を「リタイア」として全員に `raceEvent` で通知し、コースから取り除く。レースは残りの人数で続ける
- レース中の再参加は受け付けない (ロビーに戻ってからなら参加可)

### 時刻合わせ

スタートを全員同時にするため、`ping` / `pong` で往復時間を測ってホストの時刻との差を推定し (NTP と同じ考え方)、`raceStart` の時刻に合わせて各自カウントダウンする。

### ホストによる判定と不正対策

- 周回はチェックポイントを順番どおりに通過したときだけ数える (ショートカット防止)
- 前回の状態から計算して車の性能上ありえない移動 (速度上限超え、瞬間移動) は無視して警告する
- 受信メッセージはサイズ上限と形式チェックを行い、不正なものは切断する

## IP 直指定での接続手順

### 同一 LAN

1. ホストが `npm run host` を実行し、表示された LAN の IP (例: `192.168.1.10`) を伝える
2. 初回は Windows ファイアウォールの許可ダイアログが出るので「プライベートネットワーク」を許可する
3. クライアントは `http://192.168.1.10:7777` を開き、名前を入れて参加する

### インターネット越し

1. ホストはルーターで TCP 7777 をホスト PC に転送する (ポート開放)
2. ホストはグローバル IP を調べて伝える
3. クライアントは `http://<グローバルIP>:7777` を開く

注意点:

- **ポート開放できない回線がある**: キャリアグレード NAT (一部の光回線・モバイル回線・マンション回線) ではポート開放ができない。この場合は Tailscale、ZeroTier、Radmin VPN などの仮想 LAN を使えば、仮想 LAN の IP を直指定して同じ手順で遊べる
- ポートを公開すると誰でも接続を試みられるので、参加パスワード、人数上限、メッセージ検証を必ず入れる
- IPv6 のみの環境も考慮する場合は、IPv6 アドレスの入力 (`[2001:db8::1]:7777` 形式) にも対応する

## 実装ステップ (案)

1. `Transport` インターフェースと WebSocket 実装、ホストサーバーの最小構成 (接続・切断・`ping`)
2. ロビー画面 (IP 入力、参加者一覧、準備完了) を `scenes/` に追加
3. 車の状態の送受信と、他車の補間表示
4. ホストによるレース進行 (カウントダウン、周回判定、順位、結果)
5. 車同士の接触 (予測位置での判定、`collision` の中継)
6. 切断時の処理 (ホスト切断時のエラー表示とレース終了、クライアントのリタイア)、パスワード、不正対策
7. 必要に応じて WebRTC (方式 B) や Electron (方式 C) への移行を検討
